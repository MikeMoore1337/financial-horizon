# ADR-0065 - Облачная финансовая модель и offline-first синхронизация

- Статус: **принято для реализации, не реализовано**
- Дата: 2026-11-07
- Основа: main b301b9f749fb688174fc2d0986403b6d4315634e
- Решение владельца: #7, #65. Связанные: #9, #31, #32, #33, #34, #43, #45, #51, #66-#72.
- Область: архитектура и контракты. Публичная облачная синхронизация **выключена**.

## 1. Проверенное состояние репозитория

Факты на указанном SHA: браузерная БД financial-horizon-browser-v1 (структурная версия IndexedDB=1, store finance); ключи state, guest-state-v2, account-state-v2:<32-hex-user-id>, legacy-account-claim-v2. Финансовый state v2 содержит revision, entries, loans, settlements, loanPayments, categories, audit, settings. Миграция state v1→v2 и CAS выполняются в локальной readwrite-транзакции. Файл backup.js создаёт/читает отдельный контейнер financial-horizon-backup v1 (PBKDF2-SHA256, AES-256-GCM), но сама IndexedDB не зашифрована. SW кэширует публичную оболочку и исключает /api/ из своего fetch handler. FastAPI fh_email_auth использует отдельную SQLite WAL users/sessions; login не синхронизирует финансы. OAuth PR #11 ещё Draft. React/Vite #71/#72 не входят в этот ADR.

**Уточнение безопасности:** selectStateScope() сейчас копирует локальный исторический state в account-scoped key после верификации первого пользователя. Это локальная операция для совместимости, **не согласие на загрузку в облако**. Будущая синхронизация не должна запускать импорт по факту появления session cookie.

## 2. Выбранные границы компонентов

~~~mermaid
flowchart LR
  UI["PWA: текущий JS, затем React/TS #71/#72"] --> IDB["IndexedDB: облачный cache, outbox, conflict inbox"]
  UI --> LEGACY["Существующая IndexedDB v1: гость / локальное наследие"]
  IDB <-->|"HTTPS: snapshot, delta, commands"| API["FastAPI finance API #67"]
  UI -->|"same-origin session cookie"| AUTH["FastAPI email auth / OAuth #9"]
  AUTH <-->|"users/sessions"| SQLITE[("Auth SQLite WAL")]
  API -->|"внутренний session lookup, fail-closed"| AUTH
  API <-->|"транзакционные команды"| PG[("Отдельная PostgreSQL #66")]
  API -->|"обезличенные метрики"| OPS["Backup, restore, observability #45/#70"]
~~~

- API и auth работают **на одном доверенном серверном контуре**, но финансовая PostgreSQL не читает SQLite напрямую и не копирует базу иных проектов. Auth adapter разрешает действующую cookie через существующий AuthStore.current / будущую общую авторизацию PR #11 и возвращает канонический 32-hex users.id. Ни email, ни OAuth provider subject не являются финансовым идентификатором. Политика отключённой регистрации #51 неизменна.
- Finance API никогда не принимает owner_user_id/profile_id от клиента как источник прав. Клиентский profile_id может быть только запрошенным адресом ресурса, который сервер повторно авторизует. По умолчанию у пользователя один личный профиль с уникальным owner_user_id; семейные роли #43 не выдаются и не моделируются активным разрешением.
- **Новая** IndexedDB (например, financial-horizon-cloud-v1) со stores snapshot, outbox, meta, conflicts создаётся **рядом** с исходной без повышения её версии или перезаписи. Облачное состояние и outbox коммитятся атомарно в одной транзакции новой БД. Старые ключи и guest-state остаются нетронутыми. Конкретную стратегию шифрования кэша утверждать и реализовывать в #34/#68.
- Service Worker: только версии оболочки и публичных файлов; не кешировать auth/finance/API ответы, токены, операции и приватный HTML. Кэш HTTP для всех finance API: Cache-Control: private, no-store; Vary: Cookie. Конфликт между версиями приложения решается schema gate и совместимым rollback, не удалением IndexedDB.
- Полные данные можно восстановить только с сервера при сети и действующей сессии; автономная работа возможна только на устройстве с локальной копией, без обещаний постоянной доступности при сетевом сбое.

## 3. Почему operations + delta, а не замена снимков

| Подход | Плюсы | Риски | Решение |
|---|---|---|---|
| PUT полного снимка state | Просто на первом этапе | Коллизии, удаление чужих новых записей, двойной учёт платежей, невозможность точного audit | **Не использовать для команд** |
| CRDT / автоматическая last-write-wins | Удобное слияние простых заметок | Финансовые инварианты не коммутативны; удаление/оплата/перевод конфликтуют | **Не использовать для денег** |
| Идемпотентные команды + серверный журнал ревизий | Атомарные проводки, точные повторы, права и разбор конфликтов | Сложнее API/хранение outbox | **Принято** |
| Снимки для initial load/recovery | Быстрая загрузка новых устройств | Без согласованной ревизии может пропасть дельта | **Принято только для чтения** |

Первый GET /api/finance/v1/state возвращает **согласованный** снимок и сильный ETag ревизии R. Дальше GET /api/finance/v1/changes?since_revision=R отдаёт набор завершённых изменений, целыми ревизиями, по порядку, без разрывов; после применения страницы клиент сдвигает курсор только в одной IndexedDB-транзакции вместе с изменениями. Если журнал уплотнён, HTTP 410 + snapshot_required и новая загрузка снимка: локальный outbox не удаляется. Уплотнение change_log возможно только с явно объявленным min_available_revision.

Записи: POST /api/finance/v1/commands - **одна финансовая команда = одна атомарная серверная транзакция**. Клиент отправляет UUID идентификатор команды, Idempotency-Key (равен client_mutation_id), base_revision и If-Match. Сервер:
1. Проверяет Origin, сессию, права профиля и размер/схему запроса; начинает транзакцию PostgreSQL.
2. Блокирует строку finance_profiles SELECT FOR UPDATE, задаёт owner/profile контекст для RLS, проверяет **уже применённую** команду до проверки устаревшей ревизии. Тот же ключ + тот же канонический request fingerprint → прежний зафиксированный ответ; другой fingerprint → 409 idempotency_key_reuse. Ключ привязан к профилю, а не к клиенту или дате.
3. При новой команде сравнивает сильный If-Match с текущей ревизией (412 stale_revision), затем base_revision и expected_entity_revision с целевыми зависимостями (409 semantic_conflict). Если If-Match отсутствует - 428 precondition_required. Не принимает wildcard If-Match на запись.
4. Проверяет финансовую семантику/лимиты, выполняет все связанные изменения счетов/проводок/платежей, фиксирует ровно одну следующую revision и change_log + idempotency receipts **в той же транзакции**. При любом сбое откат всего блока без ответа об успехе.
5. Возвращает сохранённый ответ с revision, ETag, новым состоянием затронутых сущностей. Успех только после commit. При сетевом разрыве клиент безопасно повторяет **точный прежний запрос с прежним ключом**.

Это осознанное следование RFC 9110: несоответствие If-Match = **412**, а **409** применяется к содержательному конфликту/повторному использованию ключа; оба статуса имеют машиночитаемые коды. Код 409 не подменяет 412 ради удобства клиента. 401 = истечение сессии, 403/404 = нет доступа, 410 = курсор устарел, 422 = неправильный запрос, 429 = лимит, 503 = БД недоступна. Никакое состояние конфликта не подтверждается автоматически.

**Идемпотентность:** запись (profile_id, client_mutation_id) с hash канонизированных команды и всех предусловий уникальна и **не удаляется по TTL**, пока существует профиль; допускается компактная квитанция после срока хранения детального ответа, но она всё равно позволяет вернуть результат без повторного выполнения. Ограничить размер outbox/профиля квотами, а не временем дедупликации. Стабильный UUID команды при сетевом retry, **новый** UUID при сознательном исправлении после конфликта.

**Конкуренция:** глобальная последовательная revision профиля позволяет линейный порядок. Разные сущности могут конфликтовать глобально: безопасный клиент сначала получает deltas, проверяет dependencies и expected_entity_revision и лишь затем создаёт новый запрос с новым ключом; автоматическая повторная отправка старого mutating запроса с изменённым If-Match запрещена. Платёж, перевод, отмена, редактирование суммы, резерв и удаление требуют явного решения при семантическом конфликте. Никакого silent last-write-wins.

## 4. Офлайн и много вкладок

~~~mermaid
stateDiagram-v2
  [*] --> guest
  guest --> preparing: пользователь вошёл
  preparing --> online: snapshot получен / нет pending import
  preparing --> localOnly: нет сети / нет локальной копии
  online --> offline: сеть потеряна
  offline --> queued: локальная команда сохранена атомарно
  queued --> syncing: сеть + действующая сессия
  syncing --> online: ack + delta committed
  syncing --> conflict: 409 или 412
  conflict --> queued: осознанно сформирована новая команда
  syncing --> locked: 401 / отзыв сессии
  offline --> locked: смена аккаунта
  locked --> syncing: повторный вход в тот же user scope
  locked --> guest: выход, без очистки чужой базы
  localOnly --> online: загружен server snapshot
~~~

- Создание офлайн-команды: ID, тип, payload, основание ревизии, fingerprint, время, auth user scope, статус (pending/sending/conflict/ack) фиксируются с локальным optimistic overlay в **одной** IDB-транзакции. Не выдавать offline запись за подтверждённую банком/сервером; показывать «ожидает синхронизации».
- На новом устройстве без предварительной копии нет доступа к бюджету без сети. На старом - показывать последнюю синхронизированную версию и локальные pending действия отдельно.
- Web Locks + BroadcastChannel координируют вкладки, а при недоступности Web Locks - краткоживущий lease с fencing token в IndexedDB. Это только оптимизация: безопасность обеспечивает серверный unique(command_id) и revision. Нельзя одновременно применять один ответ к двум локальным стореджам без проверки owner scope.
- Транспорт: HTTPS с backoff+jitter, ononline/visibilitychange/manual retry; фоновая синхронизация/Push/постоянный WebSocket **не требуются**. Между устройствами: pull на входе, после commit, при возврате вкладки/соединения и периодически пока активна; опционально SSE только как сигнал «есть новая ревизия», не как доверенный источник данных.
- После 401 остановить отправку; очередь сохранить; повторный вход **того же** users.id разрешает продолжить после повторной проверки server revision. Другой users.id - отдельный зашифрованный/изолированный scope, прежняя очередь не отправляется ни под каким другим пользователем.
- Logout: прекратить запросы, отменить fetch, убрать финансовые данные и ключи из памяти/DOM, инвалидировать session, закрыть/изолировать клиентский scope; **не удалять** unsynced изменения без явного выбора и проверяемого бэкапа. Для общего устройства требуется политика lock/локального шифрования #34, так как текущие IndexedDB keys сами по себе не защищают от доступа к файлам профиля.
- Удаление сущности = tombstone с ревизией; зависимые операции и аудит не теряются. Восстановление/отмена оплаты - отдельная идемпотентная компенсирующая команда, не повторное списание.

~~~mermaid

  FINANCE_PROFILES ||--o{ ACCOUNTS : owns

  FINANCE_PROFILES ||--o{ LOANS : models
  FINANCE_PROFILES ||--o{ RESERVES : earmarks
  FINANCE_PROFILES ||--o{ LEDGER_TRANSACTIONS : posts

  OBLIGATIONS ||--o{ SETTLEMENTS : paid

  RESERVES ||--o{ RESERVE_ALLOCATIONS : allocated
  FINANCE_PROFILES ||--o{ COMMAND_RECEIPTS : deduplicates
  FINANCE_PROFILES ||--o{ CHANGE_LOG : revisions
~~~

- owner_user_id - строго 32 hex из **проверенной** auth SQLite сессии, в PostgreSQL отдельная char(32); внешний FK к SQLite невозможен: orphan/disabled проверяется через auth adapter при каждом запросе; безопасное удаление при отдельном GDPR workflow, не автоматическая каскадная реакция на login/logout.
- Все finance tables содержат profile_id и составные FK (profile_id, referenced_id). DB role приложения не суперпользователь и не BYPASSRLS, RLS FORCE + fail-closed policy дополняет обязательную проверку прав в API. Техническая учётная запись миграций - **отдельная** от runtime role.
- currency=RUB в MVP; суммы INTEGER/BIGINT в **копейках**, валидируются входным API как safe integer и на DB CHECK в допустимом пределе (предлагается 1e12 minor units на поле до отдельного решения). Float запрещён для денег. Для ставок кредита целые basis points (0.01 процентного пункта) с явной конверсией; алгоритм графика имеет версию. Для будущих валют нужен отдельный дизайн, а не конвертация существующих рублёвых сумм.
- Начальный остаток счёта задаётся явно; действительный остаток = opening_minor + SUM(signed postings), доступный = остаток - зарезервированное, «план» сам по себе не является проводкой. Транзакция типа transfer требует двух разных счетов, симметричных сумм ±N и нулевого итога. Отметка оплаты обязательства или кредита связывается с **одной** опубликованной проводкой либо без проводки до явного подтверждения. Серверный инвариант проверяется DB-триггером/транзакционной проверкой до commit, а не асинхронным отчётом.
- ID: внешний auth id остаётся 32 hex; **все новые** финансовые entity/command IDs - UUID; старые локальные id преобразуются в таблице соответствий во время подтверждённого импорта, исходные неизменны. created_at/updated_at - UTC timestamptz, календарные даты - date, recurrence - IANA timezone + дата и rule; не использовать время устройства как авторитетное revision.
- Таблицы change_log и receipts фиксируют actor (internal opaque id), server timestamp и тип, но не секреты, email или значения операций в технических логах. Доступ к audit-содержимому такой же приватный, как к финансам.
- Семейный бюджет #43: профиль как граница данных и rev/permission scope, без membership/ACL в v1. В будущем отдельная membership с ролями и ключами после отдельного security/crypto review. Никаких прав доступа через угадывание profile UUID.

## 6. SQL-доступ и миграции

**Рекомендация:** SQLAlchemy 2.x (типизированные ORM entities/transactions; Core для массовых postings и журналов) + Alembic (явные, ревьюируемые forward migrations, ручная проверка autogenerate). PostgreSQL driver psycopg 3 (синхронная транзакционная модель; async только после подтверждённой нагрузки). Использовать request-scoped Session.begin(), короткие транзакции, SELECT FOR UPDATE, вставку квитанции с UNIQUE, необязательные retry только при однозначно повторяемых serialization failures. Никакого SQL из полей клиента, минимальный пул и таймауты по измерению VPS.

**Альтернативы:** raw SQL экономит зависимости, но увеличивает число ручных схем/проверок; SQLModel упрощает DTO, но усложняет границы migration/domain; Tortoise/другая ORM не даёт преимуществ проекту. **Alembic autogenerate - черновик**, не миграция без человеческого контроля. На больших таблицах: expand → dual-read (где нужно) → backfill batches → validate → contract; создание индексов CONCURRENTLY отдельно от обычной транзакции, обратная совместимость двух версий клиента, schema_version и обязательный backup/restore. Не изменять SQLite auth в #66.
