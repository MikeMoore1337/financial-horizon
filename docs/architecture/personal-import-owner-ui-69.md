# #69 - ручной перенос локальной бухгалтерии в личный облачный профиль

**Статус: source-only / DEFAULT OFF / PRODUCTION NOT VERIFIED.**

Владелец отказался от обязательных LUKS2, offsite-сервера и PITR. Для личного
сценария необходимо только гарантировать, что перенос не уничтожит локальные
данные и что зашифрованную копию реально можно восстановить.

## Как работает интерфейс

В настройках, внутри карточки «Зашифрованная копия», кнопка «Перенести данные
в аккаунт» появляется, только если `fh-finance-accounts=enabled` и
`fh-finance-import=enabled`, текущий пользователь FH подтверждён и гость
выключен. В настоящем `index.html` оба флага по умолчанию `disabled`.

1. Пользователь **предварительно сохраняет зашифрованный AES-GCM-файл вне
   браузера**. Затем выбирает его и вводит пароль в локальном диалоге.
2. Предпросмотр подтверждает текущую FH-сессию, извлекает только сервером
   выданный profile UUID, проверяет пустой подтверждённый /state и сильный
   ETag. Четыре отдельные проверки старой IndexedDB и внешнего backup
   сопоставляют данные и SHA-256 (двойная проверка preview + новая
   независимая проверка перед построением payload). Сервису не передаётся
   пароль или локальная копия до следующего явного шага.
3. Пользователь читает количество обязательств, кредитов, фактических оплат
   и платежей, отдельно отмечает согласие и нажимает «Перенести на сервер».
   Перед отправкой проверяется неизменность локальных данных и FH-сессии.
4. Backend должен быть явно включён через `FH_FINANCE_RUNTIME_MODE=personal`,
   `FH_FINANCE_V2_RUNTIME=on`, `FH_FINANCE_IMPORT_RUNTIME=on`.
   Запросы staged manifest, одноразового commit и byte-exact recovery
   выполняются под тем же отзывным FH cookie с проверками Origin, If-Match,
   RLS и серверной транзакционной квитанции.
5. Если связь прерывается после отправки, **нет автоматического повтора**.
   Исходный IndexedDB и отдельная AES-копия не изменяются. Без проверки
   серверной квитанции нельзя объявить повторный импорт безопасным.

## Обязательное до включения

На VPS должны работать личная PostgreSQL с изоляцией, закрытая FH-сессия,
защищённый backend, обычная шифрованная копия и проверенное восстановление.
После этого требуются smoke на установленной PWA, один проверенный импорт
обезличенной контрольной копии, подтверждение сервера и rollback приложения.
Проверки source-only, WebKit/Chromium CI не заменяют эти действия.

**До окончания #68** локальная бухгалтерия остаётся основным рабочим
интерфейсом. Синхронизация и безопасное разрешение конфликтов не активированы.
Не редактировать одну и ту же бухгалтерию одновременно на двух устройствах.
Физическая приёмка устройства и действующий production backup/restore пока
`NOT_VERIFIED`; Issue #69 нельзя закрывать только по PR.
