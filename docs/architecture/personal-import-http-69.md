# #69 - подтверждённый персональный HTTP-импорт

**Source candidate, DEFAULT OFF.** Включается только после установки и реальной
приёмки личной PostgreSQL, вместе с `FH_FINANCE_RUNTIME_MODE=personal`,
`FH_FINANCE_V2_RUNTIME=on` и отдельным `FH_FINANCE_IMPORT_RUNTIME=on`.
Другие режимы игнорировать нельзя - сервер запрещает включать импорт без v2.

Локальный источник остается в IndexedDB и никогда не удаляется. Владелец
сначала отдельно экспортирует и проверяет AES-GCM-копию, затем через
`planLiveLegacyImportPreviewCandidate` подтверждает неизменность исходных
данных и SHA-256. HTTP-транспорт **не может доказать физическое наличие**
внешней копии по заявлению клиента: этот факт подтверждается браузерным
чтением/дешифрованием и отдельной пользовательской проверкой восстановления.
До подключения UI нельзя назвать реальную миграцию принятой.

## Версионированные операции

Все вызовы требуют действительную защищённую FH-сессию, ранее выданный
`fh_finance_session` cookie, совпадающие Origin/Fetch-Site и лимиты
запросов, без client-supplied user_id или profile_id. Сессия перепроверяется
после получения тела запроса и непосредственно до SQL.

- `POST /api/finance/v1/import/manifest`: JSON
  `{"manifest": <strict manifest-v1>}`. HTTP `If-Match` должен совпадать
  со strong ETag неизменённой серверной ревизии. Результат 202
  `UNVERIFIED_MANIFEST_STAGED` или 200 при идемпотентном повторе.
  Только metadata и deterministic record-map, деньги не изменяются.
- `POST /api/finance/v1/import/commit`: JSON
  `{"manifest": <тот же manifest-v1>, "source_canonical_json": "<канонический JSON>"}`.
  Проверяются **фактические байты** и SHA-256, совпадение состава с
  подготовленной картой, owner/RLS, пустое исходное серверное хранилище,
  base revision, все денежные инварианты. Одна SQL транзакция создаёт
  obligations/loans/historical fact records, архив исходных байт, неизменяемый
  receipt, журнал и новую ревизию. 201 - первый commit, 200 - точно такой
  же повтор (без второй денежной операции). Обычная ошибка не сдвигает
  ревизию и не оставляет частичных записей.
- `POST /api/finance/v1/import/restore`: JSON
  `{"batch_id":"<UUID>","source_sha256":"<SHA256>","confirm_restore":true}`.
  Возвращает **оригинальные проверенные JSON-байты**, только владельцу
  соответствующего профиля, с `Cache-Control: private, no-store` и
  attachment. Это *чтение*, не восстановление с заменой IndexedDB;
  браузер должен сохранить полученные байты в зашифрованную копию до
  любого применения.

Ответы не раскрывают полный источник или финансовые суммы в логах/ошибках.
Максимум тела staging 2 MB, commit 10 MB, restore 2 KB; повторные поля JSON
отклоняются. Внешние HTTP POST операции запрещены по Origin. При 401, 409,
412 или 503 клиент должен показать пользователю статус без автоматического
повтора неизвестного списания.

## Что осталось до закрытия #69

Подключить реальный пользовательский выбор и ручное подтверждение импорта
после независимого восстановления сохранённого AES-GCM-архива, включить
private API только после целевого PostgreSQL backup+restore и выполнить
настоящую приёмку в установленной PWA на двух клиентских контекстах.
Пока HTTP-транспорт - только исходный код и синтетические PostgreSQL/FH
AuthStore тесты. Никакая реальная пользовательская запись не загружалась.
