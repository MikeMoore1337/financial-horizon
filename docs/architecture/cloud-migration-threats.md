# #65 - Миграция, угрозы, криптография и эксплуатационная приёмка

**Статус:** архитектурный проект, не работающий backend. Основные материалы: [ADR](ADR-0065-cloud-finance-sync.md), [SQL](cloud-finance-schema.sql), [OpenAPI](finance-sync-v1.openapi.json). Публичная облачная синхронизация запрещена до #70/#51.

## 1. Шифрование: решение и альтернативы

| Свойство | Шифрование на сервере и отдельно на клиенте (принято для v1) | Настоящее E2EE (отложено, нужен отдельный ADR) |
|---|---|---|
| Финансовые суммы на сервере | Расшифрованные данные при проверках и построении отчётов | Только ciphertext; отчёты рассчитывает клиент |
| Восстановление пароля login | Не уничтожает данные PostgreSQL | Не восстанавливает DEK; нужен отдельный recovery key |
| Новое устройство | Вход + серверный snapshot, затем локальная разблокировка #34 | Перенос ключа с другого устройства или recovery package |
| Семья #43 | Серверный ACL, аудит и разделение пространств | Конверты ключей участникам, смена ключей при отзыве, проблема старых копий |
| Потеря ключа | Restore key для PostgreSQL backup хранится независимо | Без устройства или recovery key данные нельзя расшифровать |

**Выбрано:** отдельная PostgreSQL под контролем приложения, HTTPS/TLS, encrypted filesystem volume, независимо зашифрованные backup+WAL, OS/DB least privilege и возможность проверки серверных денежных инвариантов. Это **не E2EE**, и не следует объявлять серверное шифрование реализованным без проверки реального deployment. Auth SQLite также имеет отдельный protected backup. Никакие данные других проектов не используются.

**Связь с #34:** IndexedDB сейчас plaintext. Задача #34 должна реализовать локальную защиту через Web Crypto, версионированный envelope с AES-GCM, отдельный KDF/recovery/unlock UX, уникальные nonce, целостность и безопасную миграцию v1/v2. Ключи не хранить в localStorage/исходниках/Service Worker/логах; cookie и пароль входа не являются ключом финансов. Offline после успешного unlock допустим, но XSS или расширение могут прочесть рабочую память: шифрование диска не решает этот риск. До выполнения #34 не обещать локальную защиту и не включать cloud без отдельной оценки остаточного риска.

Если впоследствии E2EE принято: client-generated DEK, user-managed KEK/recovery key, envelope для каждого устройства, authenticated key exchange, rotation и revocation, протокол совместного доступа #43, отказ в восстановлении ciphertext при потере всех ключей. Никаких маркетинговых заявлений до независимой проверки реализации и восстановления. E2EE не заменяет auth, TLS, idempotency и защиту XSS.

## 2. Модель угроз

Границы: браузер/локальный профиль; сеть/reverse proxy; FastAPI/AuthStore/SQLite; отдельная PostgreSQL; оператор и backups.

| Угроза | Приоритет | Обязательная защита / проверка |
|---|---|---|
| IDOR и горизонтальный доступ | Critical | Сервер извлекает users.id из действующей сессии, проверяет owner, составные FK + FORCE RLS; другой аккаунт получает 403/404 без чужих данных |
| CSRF с HttpOnly cookie | Critical | Проверка Origin/Fetch Metadata для каждого изменяющего запроса, same-origin, запрет credentialed cross-origin CORS; SameSite недостаточно |
| Повтор POST после таймаута | Critical | Unique(profile_id,client_mutation_id), fingerprint + receipt в одной транзакции; повтор с иным payload = 409 |
| Потеря правки | Critical | ETag/If-Match = 412; expected entity revisions и семантические конфликты = 409; никакого last-write-wins |
| Двойной платёж/перевод | Critical | Строгие signed postings, одинаковый профиль, две противоположные проводки; ledger_payment_links один к одному, компенсация вместо удаления |
| Смена аккаунта/истечение cookie | Critical | Очередь scoped по проверенному users.id, 401 блокирует flush, другой аккаунт не видит/не отправляет прежнюю очередь |
| XSS/расширение/доступ к IndexedDB | High | CSP, кодирование вывода, безопасные зависимости; шифрование и unlock через #34, риск открытой RAM документировать |
| Утечка БД, ключа или backup | High | Отдельный runtime role без BYPASSRLS, encrypted disk + off-host backups, ключ отдельно; запрет персональных логов |
| Replay delta, старый Service Worker | High | HTTPS, no-store, per-profile cursor, монотонная revision, schema gate, /api/ не кэшируется SW |
| Вредоносный импорт | High | AES-GCM tag, max size/rows, validateState, точные minor units, предварительный preview, серверная повторная валидация |
| Заполнение диска / throttling | Medium | Мониторинг WAL/пула, квоты запросов и outbox, fail-closed 503 вместо ложного ACK |

В логах допустимы только обезличенные request ID, код ошибки, длительность, число конфликтов и возраст backup. Запрещены суммы, названия транзакций, email, финансовые payload, токены, cookie, KDF material и содержимое шифрованных/расшифрованных файлов. Секреты только в защищённой конфигурации.

**Нюанс разных БД:** нет общей ACID транзакции между SQLite auth и PostgreSQL finance. Подлинность сессии проверяется перед финансовой записью, при необходимости повторно в критической секции; мгновенный отзыв сессии во время commit может давать ограниченное race window. Для строгой отзывчивости определить session generation/revalidation в #67; не обещать межбазовую атомарность.

## 3. Гарантии миграции существующей IndexedDB → PostgreSQL (#69)

~~~mermaid
flowchart TD
  A["Локальный guest/account state v1/v2"] --> B["Согласованное чтение, validateState, migration in memory"]
  B --> C["Зашифрованный backup v1 на устройстве"]
  C --> D{"Расшифровка и SHA-256, counts, sums проверены?"}
  D -- Нет --> STOP["Остановить, локальная БД не тронута"]
  D -- Да --> PREVIEW["Предпросмотр + выявление дубликатов"]
  PREVIEW --> OK{"Явное подтверждение владельца?"}
  OK -- Нет --> STOP
  OK -- Да --> CHECK["Проверить auth user и текущую cloud revision"]
  CHECK --> DUPS{"Облачный профиль непустой или есть конфликт?"}
  DUPS -- Да --> REVIEW["Выбор: пропустить точные дубликаты или отменить"]
  DUPS -- Нет --> STAGE["Изолированное staged upload"]
  REVIEW --> STAGE
  STAGE --> COMMIT["Серверный atomic commit + receipts + change log"]
  COMMIT --> VERIFY["Сверка snapshot/ID/сумм; сохранение backup"]
~~~

1. **Выбор источника:** отдельно отображать guest-state-v2, account-state-v2 по проверенному users.id и исторический state. Локальная функция selectStateScope может копировать legacy на аккаунт, но это НЕ согласие на cloud upload. Нельзя копировать данные владельца U1 в U2 даже при повторном login.
2. **Стабильный снимок:** локальный CAS и временная блокировка мутаций в других вкладках, validateState для v1/v2, преобразование **только в памяти**, неизменность суммы/источника. Экспорт через существующий backup.js формата financial-horizon-backup v1 (PBKDF2-SHA256 / AES-GCM). Пароль backup серверу не передавать. Проверка расшифровки в отдельном изолированном контексте, проверка SHA-256 ciphertext, числа записей и суммы в копейках. Непроверенный backup = STOP.
3. **Preview:** показать исходные записи, числа, суммы, целевой облачный профиль и возможные совпадения. Exact dedupe: (profile_id, source_sha256, record_type, legacy_record_id) → target UUID в import_record_map, ключ хранится до удаления профиля. Совпадение даты/суммы при разных legacy IDs лишь подозрение на дубль, без автоматического слияния. Старые encrypted backup v1 с payload v1/v2 должны продолжать читаться.
4. **Согласие:** явное действие пользователя для выбранного аккаунта, визуально понятное предупреждение, что сервер получит расшифрованные финансовые записи (в принятой v1 модели). Обычный login не запускает импорт. При непустом cloud budget безусловно **запретить overwrite**; в первой версии доступны только skip_exact либо cancel, не silent merge.
5. **Stage/commit:** staged upload только после согласия, ограничение размера/chunk count, серверная повторная валидация всех FK и целочисленных сумм, стабильные UUID mappings. Commit одной транзакцией после проверки ETag, импортной политики, session и отсутствия конфликтов. Change log, receipts и все записи атомарны. Повтор chunks/commit с тем же ключом не дублирует записи.
6. **Прерывание:** сохранить batch_id и idempotency key локально. После неизвестного ACK прочесть status batch/snapshot (будущая реализация #69) и сверить counts, суммы, mapping; не начинать новый импорт с новым ключом вслепую.
7. **После:** исходная IndexedDB, encrypted backup и проверяемая квитанция остаются до успешного независимого восстановления. Не удалять local state и unsynced outbox при rollback. Если другие устройства уже записали данные, не делать массовый rollback через PUT snapshot; использовать только явные доменные компенсирующие команды.

**Fail-closed условия:** неверный пароль/tag, неизвестная версия схемы, дробные/небезопасные денежные значения, повторный legacy ID, неподтверждённый аккаунт, старый If-Match, нарушение FK, изменённый fingerprint, неполный chunk, существующий конфликт. Не выдавать частичный import за успех.

## 4. Надёжность и эксплуатационные цели

Для #45/#66 предлагаемые, пока **не подтверждённые** целевые значения: RPO <= 15 минут и RTO <= 4 часов для подтверждённых сервером команд. Не применяются к локальным pending без backup. Нужны PostgreSQL base backups + WAL PITR, отдельное хранение encrypted copies и ключа, hash verification, независимый restore drill ежемесячно, резервная копия SQLite auth с согласованным WAL и отдельная проверка входа. Предлагаемая ротация: ежедневные 7, еженедельные 4, ежемесячные 3 с корректировкой после оценки диска. Проверять доступное место и размер WAL заранее.

Rollout вне #65: feature flag OFF, изолированный upgrade/downgrade compatibility, backup/restore, RLS/IDOR/CSRF/повторы, реальный multi-device E2E, обязательный CI exact SHA, независимое security-review и операторский approval. Затем контролируемый production deploy, smoke и готовый *schema-compatible* rollback без DROP/DATABASE downgrade. При повреждении - API read-only/OFF + roll-forward. Публичная регистрация #51 не включается этим процессом.

## 5. Матрица E2E для последующих задач

| Сценарий | Ожидаемый результат |
|---|---|
| U1-A → U1-B | Команда A R→R+1, delta B идентична серверу |
| U1-A ↔ U2-B | Чужой profile/entity не читается и не меняется |
| U1-B offline → reconnect | 2 pending с теми же mutation IDs, без двойной оплаты |
| U1-A1 ↔ U1-A2 (вкладки) | Lock/fencing + server revision, нет silent overwrite |
| U1-A ↔ U1-B (одна сущность) | 412/409, ручная сверка; no data loss |
| U1-A ↔ U1-B (разные сущности) | Дельта и осознанный rebase, обе команды сохранены |
| Logout U1 → login U2 | Очередь U1 не отправляется под U2, cache изолирован |
| 401, новая сессия U1 | Pending сохранены, после входа безопасный retry |
| Один Idempotency-Key дважды | Ровно один ledger transaction + receipt |
| Один ключ, другое тело | 409; исходная команда сохранена |
| Устаревший delta cursor | 410 + snapshot, outbox не удалён |
| Отказ БД после BEGIN | Не существует ложного успешного ACK |
| Старые v1/v2 и backup v1 | Backup verify, preview, consent, exact dedupe, не меняется legacy |
| Restore / PITR | RPO/RTO фактически измерены в отдельной среде |
| Старый SW / PWA | /api не кэшируется, IndexedDB сохраняется |
| Physical Safari | Проверка настоящего iOS PWA, а не эмуляции Chromium |

**#65 тестирует только документы и синтетические контракты.** Ни production Postgres, ни реальные FastAPI endpoints, ни E2EE, ни RPO/RTO, ни перенос данных этим PR не проверены.
