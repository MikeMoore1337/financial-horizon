# Модель данных и безопасные миграции (#32)

## Текущий контракт

IndexedDB: `financial-horizon-browser-v1`, версия структуры **1**, object store `finance`. Ключи: `state` (неизменяемый исторический источник при первой привязке), `guest-state-v2`, `account-state-v2:<opaque-user-id>`, `legacy-account-claim-v2` (только маркер принадлежности). Никакие записи не передаются на сервер; авторизация и хранилище физически независимы.

Объект состояния v2: `{version:2,revision:<safe integer>,entries:[],loans:[],settlements:[],loanPayments:[],categories:[],audit:[],settings:{currency:'RUB'}}`. Значения `amountCents`, `openingCents`, `paymentCents` и суммы строк графиков - **целые копейки**. Коллекции не пересоздаются и не нормализуются при v1 → v2. Дополнительные поля записей сохраняются. `revision` - счётчик успешных локальных записей внутри одного ключа, а не сумма/время.

`finance.js` - расчёты и валидация состояния; `state-migrations.js` - чистые преобразования v1 → v2 и аварийное обратное преобразование; `storage.js` - IndexedDB, транзакции, ревизии, выбор области; `ledger-operations.js` - записи, кредиты, платежи, история изменений; `app.js` - DOM, формы, отображение, события, авторизационный маршрут; `backup.js` - неизменённый формат шифрованного контейнера.

## Гарантии и границы

1. Состояние v1 проверяется до миграции; миграция меняет только `version` и добавляет `revision=0`. В IndexedDB чтение с миграцией и запись нового состояния происходят **в одной readwrite-транзакции**, затем ожидание `tx.oncomplete`. При abort исходная v1 запись сохраняется.
2. Режимы аккаунта и гостя остаются изолированными. Исторический `state` не перезаписывается при первом копировании в аккаунт. Уже сохранённые другие ключи мигрируются только при непосредственном доступе.
3. Любая мутация перечитывает состояние внутри той же транзакции и проверяет `expectedRevision`. Открытые формы сохраняют исходную ревизию до отправки, даже если BroadcastChannel обновил экран; действия с подтверждением (очистка, восстановление, архивирование и отмена оплаты) тоже фиксируют ревизию до запроса подтверждения. При несоответствии запись отклоняется; пользователь должен повторно открыть форму. BroadcastChannel ускоряет обновление интерфейса, но не служит блокировкой.
4. Некорректная или неизвестная будущая `version`, испорченная сумма и неверный счётчик останавливают запись. Более старая открытая вкладка с v1-кодом не может перезаписать v2: прежний `validateState` отклоняет её. При повышении структурной версии IndexedDB соединения закрываются через `onversionchange`.
5. `backup.js` сохраняет прежний контейнер `version:1` с AES-256-GCM / PBKDF2-SHA256. Внутренний payload может быть v1 или v2. Старые копии читаются без изменения шифра/пароля; после подтверждения восстановления payload v1 мигрируется перед атомарной записью.
6. Service Worker создаёт **отдельный** кеш оболочки, обновляет файлы с принудительной повторной загрузкой и сохраняет прежний обход `/api/`. Суммы не кэшируются. В офлайне установленная старая PWA остаётся способна прочитать v1; после миграции на v2 старая версия безопасно откажет вместо записи по старой схеме.

## Восстановление и откат

Перед выкладкой проверить экспорт **и реальное восстановление** v1 AES-GCM-копии в отдельном браузерном профиле с настоящей IndexedDB. Не собирать финансовые записи пользователей в CI. Важное ограничение: после первого чтения новой версии пользовательская IndexedDB уже v2, и простой возврат статических файлов старой v1-версии **не восстановит работоспособность** (прежний `validateState` отклоняет v2). Нельзя выполнять rollback только переключением ссылки на предыдущий v1-only релиз.

**Предпочтительный production rollback - совместимый аварийный статический комплект:**

1. **До** публикации сохранить полный SHA и контрольные суммы статических файлов предыдущего релиза, подготовить отдельный, закрытый от обычной выдачи каталог rollback. Взять HTML, CSS, `app.js`, `account.js` и иные файлы UI из предыдущего рабочего релиза.
2. Заменить в аварийном комплекте **только слой совместимости** файлами из проверенного v2-релиза: `finance.js`, `storage.js`, `state-migrations.js`, `ledger-operations.js`, `sw.js`. Для `sw.js` использовать отдельное, уникальное имя CacheStorage, принудительно обновляемый список всех модулей и ту же защиту обхода `/api/`. Записать исходные SHA, состав комплекта и SHA-256 всех файлов вне веб-каталога. Не менять backend авторизации.
3. Проверить аварийный комплект на изолированном origin с настоящей IndexedDB и Service Worker: v1→v2, создание новой записи, смена активного worker на аварийный, чтение всех сумм с v2, запись/офлайн и обратное обновление штатного worker. Без этой проверки аварийный комплект **не считается готовым к переключению**.
4. При критическом дефекте остановить новые публикации, проверить закреплённый аварийный каталог и атомарно переключить серверную ссылку именно на **совместимый** комплект, а не на старый v1-only релиз. В клиенте должна остаться `version:2`; секреты и финансовые записи не копируются на сервер. Подтвердить SHA ресурсов по публичному HTTPS, затем проверить новую и уже установленную PWA, офлайн/онлайн, два профиля и восстановление. После исправления выполнить контролируемый roll-forward на совместимую версию v2.

Для настоящего #32 на отдельном Windows/Edge origin проверена совместимая комбинация старого UI до #32 (основа `8610ff75`) с v2-слоем из `88963fdd`: **6/6 PASS** (чтение и запись v2, отсутствие изменения копеек, офлайн, rollback и roll-forward). Это лишь изолированная проверка - production-комплект готов только после размещения, хеширования и сверки на целевом сервере.

**Аварийное понижение клиентской версии состояния до v1** допускается только на конкретном контролируемом устройстве при подтверждённой резервной копии, закрытых вкладках и осознанном отказе от v2. Выполнить в DevTools текущей v2-версии на том же origin:

```js
await (await import('./storage.js?rev=auth-scopes-v18')).rollbackAllScopesToV1()
```

Метод откатывает `state`, `guest-state-v2` и аккаунтные ключи в одной транзакции, не меняя суммы и операции; при повреждённой записи откатывается вся транзакция. **Если обнаружен хотя бы один `encrypted-cutover-fence-v1:<state-key>`, весь откат запрещается и транзакция прерывается, сохраняя исходные версии и значения всех профилей.** Нельзя вручную удалять fence ради обхода запрета: после возможных зашифрованных операций/синхронизации прежний снимок может быть устаревшим, а долговечная очередь потеряется. Такой случай требует отдельно проверенного восстановления защищённого хранилища, согласования всех источников и подтверждения владельца конкретного профиля. **Это не удалённая массовая миграция устройств** и не основной план серверного отката: нельзя вызывать её автоматически после обычного сбоя или ожидать её выполнения во всех установленных PWA. Никогда не удалять IndexedDB и CacheStorage с финансовыми данными ради отката; при невозможности доступа к базе - использовать ранее проверенный зашифрованный экспорт.

## Изоляционные проверки

`node --test tests/*.test.mjs`: миграция v1 и копии, неизменность копеек, повторный запуск, отказ неизвестной версии, исключение внутри транзакции, имитация сбоя записи, разные вкладки / CAS, независимые ключи. Браузерная IndexedDB / PWA и реальный вход-выход должны пройти отдельную проверку на изолированном origin до production. Полная E2E-инфраструктура вынесена в #31.
