# Financial Horizon #41 - расчёты финансовой аналитики

## Область изменения

Это отдельный read-only модуль `src/domain/analytics/`. Он не меняет финансовые записи, не обращается к IndexedDB, PostgreSQL, сети или сторонним службам и не подключён к существующим экранам. Данные передаются вызывающим кодом только после проверки авторизации, профиля и целостности журнала. Доменный модуль не предназначен для прямого принятия недоверенных HTTP-запросов.

- `buildAnalyticsReport(input)` - отчёт за включительный интервал дат, помесячные итоги, план/факт, категории, 5 крупнейших положительных статей расходов, проверенные временные ряды и готовые данные для диаграмм.
- `compareReportMonths(report, current, previous)` и `compareReportPeriods(current, previous)` - сравнение сумм и процентных изменений. Процентное изменение возвращается **в базисных пунктах** (`10000` = `100%`, `2500` = `25%`); при нулевой базе или отсутствующей истории возвращается `null`.
- `exportAnalyticsCsv(report)` - *только* создание строки CSV в памяти. Скачивание возможно исключительно по явному действию пользователя в будущем UI.

Деньги хранятся и передаются в целых копейках RUB. Входная сумма движения ограничена величиной `MAX_MINOR = 1_000_000_000_000` модели #33; накопленные суммы проверяются на `Number.isSafeInteger` и при переполнении приводят к ошибке. Даты - ISO `YYYY-MM-DD` без локального часового пояса; начало и конец периода включены.

## Важные правила агрегирования

1. Входные `AnalyticsTransaction` представляют **один логический факт операции**, а не отдельную проводку банковского счёта. `signedMinor` - проверенный суммарный эффект всех проводок операции по собственным счетам. Идентификаторы не могут повторяться.
2. `income` всегда имеет положительный эффект, `expense` - отрицательный. Подтверждённый `payment` может быть положительным (поступление по обязательству) или отрицательным (оплата обязательства/кредита). Не добавлять `settlements` или `loanPayments` повторно, если они уже представлены в журнале `payment`.
3. `transfer` и `reservation` имеют нулевой суммарный эффект и исключаются из дохода и расхода. `adjustment` отражает техническую коррекцию остатка и **не классифицируется** как доход/расход без дополнительного решения предметной области. Начальные остатки не являются доходами.
4. Для `reversal` обязательна ссылка `reversedTransactionId` на существующую исходную операцию. Суммарный эффект должен быть точно противоположным, категория наследуется от неизменяемого исходного события. Компенсация включается **в месяц своей даты**, а оригинальная проводка остаётся в историческом месяце. В результате в месяце компенсации допустим отрицательный расход или доход. Вторая компенсация и сочетание `voidedAt` с компенсацией отклоняются. Отдельное логическое `voidedAt` без компенсирующей операции исключает запись из отчёта.
5. Архивные категории сохраняются. Для неизвестной категории используется подпись «Неизвестная категория», исходный идентификатор не включается в CSV. Перемещение расхода между категориями меняет только группировку при новом расчёте, не общую сумму.
6. Общий месячный план (`scope: 'total'`) **не суммируется** с планами категорий (`scope: 'category'`). Отсутствующий план - `null`, не ноль. Отклонение план/факт также равно `null`, если отсутствует фактическая история в месяце; общее отклонение для нескольких месяцев требует фактической истории в каждом месяце, чтобы не выдавать отсутствие записей за экономию. Для неполных календарных месяцев план/факт не рассчитывается, чтобы не подменить месячный лимит частичным. Для многомесячного периода итоговый план возвращается только при наличии полного плана за каждый месяц.
7. `hasActual=false` и значения `null` в `charts.cashflow` обозначают отсутствие фактической истории, в отличие от подтверждённого нулевого результата. Отсутствующие снимки долга/накоплений не интерполируются и не заполняются нулями. В CSV отсутствие фактических сумм представлено пустыми полями и отметкой «нет», а не ложными нулями. Отметки логической отмены принимаются только в строгом формате UTC ISO timestamp.
8. Круговая диаграмма использует **положительные чистые суммы категорий**, возвращая доли в базисных пунктах (сумма ровно `10000`). Категории с нулевым/отрицательным нетто-расходом не становятся отрицательными секторами; возвраты видны в табличных суммах. Это доля положительных категорий, **не** доля от общей суммы расходов после возвратов.

## Контракт будущего адаптера к #33 (предложение для согласования)

**Не подключать адаптер автоматически, пока #33 PR #84 и API #67 не стабилизированы.** Источник истины для облачного пользователя - авторизованный серверный журнал, для гостя - проверенный локальный журнал своего профиля.

1. Принять тип `LedgerState` из #33, проверить его через `assertLedgerState` и проверить принадлежность профилю. Дальше брать `transactions` и `postings` одного проверенного снимка и одной ревизии (никаких смешанных страниц истории). `id -> postings[]`, `signedMinor = sum(postings.signedMinor)` с контролем безопасных целых. Для `transfer` с двумя ногами - ноль, а не две операции аналитики. Для `reversal` использовать поле `reversedTransactionId`, не трактовать её как новое поступление без ссылки. Приоритет отмены - append-only компенсации #33; `voidedAt` - для других явно согласованных источников без такой пары.
2. `paymentLinks` используются только для получения **подтверждённой классификации** оплат и категории из источника платежа. Разрешение категорий прямых операций #33 ещё не предусмотрено: нужен согласованный неизменяемый `categoryByTransactionId` и категория исходного события для компенсаций, с явным вариантом «Без категории» при отсутствии связи. Не угадывать категорию по назначению платежа, note или имени счёта. Не добавлять незачисленные плановые платежи в фактические движения.
3. Бюджеты #35 должны предоставлять типизированные месячные `total`/`category` планы по направлениям доход/расход. Повторяющиеся планы разворачивает владеющий ими домен; аналитика не пишет лимиты и не считает одни и те же категории дважды.
4. Долговой ряд: только **проверенные фактические остатки** из #39/#33, а не прогнозные строки графика, с точной датой снимка. Ряд накоплений: только агрегированные остатки **добровольных** целей #37; выделенные резервы обязательств #6 не смешивать с целями. В аналитический модуль передаётся один общий снимок на дату, не список отдельных кредитов/целей; чтобы не удвоить баланс, суммирование контролирует владеющий домен.
5. Источник адаптера обязан исключить чужие/дублированные профили и неполные страницы; при сбое не показывать правдоподобный, но неверный отчёт. Валидировать исправление категории после компенсации по неизменяемой исходной записи. Требуются совместные интеграционные фикстуры #33/#35/#37, сверка SQL/API, тест независимых профилей и rollback до подключения UI.

Эти пункты пока **не утверждённый контракт интеграции**. Конкретный адаптер, чтение пользовательского состояния и UI намеренно не включены в данную ветку.

## CSV и конфиденциальность

Формат: UTF-8 BOM, разделитель `;`, CRLF, строки «месяц», «категория», «долг», «накопления»; суммы - **целые копейки** (не локализованные строки рублей). Текстовые ячейки экранируются по CSV (в том числе кавычки и переносы строк), значения с опасным началом `=`, `+`, `-`, `@` после пробелов/табуляций/непечатных префиксов дополнительно получают ведущий `'`, чтобы их не интерпретировали как формулы. Экспорт не содержит ФИО, имён учётных записей, идентификаторов профиля/транзакций, заметок, токенов или иных приватных метаданных. Категории и итоговые суммы остаются чувствительными данными, поэтому пользователь должен сам инициировать скачивание.

## Проверка и критерии готовности

Синтетические тесты: сверка с независимым арифметическим эталоном, перенос категории, income/expense/linked payment, исключение transfer/reservation/adjustment, отмены и восстановление, переполнения, дробные/нулевые/отрицательные значения, полные/неполные месяцы и високосные даты, пустая история, архивные категории, долг/цели, безопасный CSV, перестановка и 50 000 операций. Изолированная строгая проверка TypeScript предусмотрена отдельным тестом.
