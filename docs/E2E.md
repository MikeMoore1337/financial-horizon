# Реальные E2E - Financial Horizon #31

## Что именно проверяется

Используется Playwright/Chromium на **реальном локальном HTTP origin** `http://127.0.0.1:8791`. `tests/e2e/server.py` запускает штатный FastAPI `create_app()` и настоящий SQLite `AuthStore`. Приложение, обработчики маршрутов, IndexedDB, cookies, Service Worker, бизнес-логика шифрования и импорта XLSX не подменяются.

**Только внешние зависимости** изолированы: SMTP заменён временным хранилищем токенов писем только для адресов `*.invalid`, а Turnstile заменён тестовым браузерным скриптом и тестовой серверной валидацией. Такой обход категорически **не переносится на production**. Тестовый HTTP-сервер слушает исключительно loopback. Данные SQLite удаляются после остановки процесса. Каждый тест создаёт синтетические записи в новом браузерном контексте; персональные финансовые данные не нужны.

| Область | Реальные проверки |
| --- | --- |
| Хранилище | Нативная IndexedDB, целостность сумм после перезагрузки, разные браузерные профили, обновление во второй вкладке |
| Аккаунт | UI регистрации, письмо-подтверждение через изолированную тестовую почту, серверная сессия и HttpOnly cookie, выход/повторный вход, два пользователя и гость, отзыв других сессий, смена email |
| Финансы | Создание доходов/расходов/кредитов, редактирование, фактические оплаты, отмены, архив/восстановление |
| XLSX | Подлинный файл ZIP/XLSX с вымышленными записями, загрузка через `input[type=file]`, предварительный просмотр, повторный импорт без дублей |
| Резервная копия | Настоящий зашифрованный экспорт браузером, очистка локального хранилища и восстановление из скачанного файла |
| PWA | Нативная регистрация и управление Service Worker, кэш оболочки, офлайн/онлайн перезагрузка, смена ревизии SW без потери IndexedDB, `manifest.webmanifest` |
| UI/сеть | Переключение светлой/тёмной тем, 320/390/1280 px, все разделы, отсутствие незапланированной горизонтальной прокрутки, ошибки JavaScript и внешние запросы |

Тесты работают с настоящими входами и событиями интерфейса. Чтение IndexedDB напрямую выполняется **только как независимая проверка результата**, без записи в базу или подмены API.

## Чистое воспроизведение

Linux (Python 3.12+ и Node 24):
```sh
npm ci
python3 -m pip install -r backend/requirements-test.txt
npx playwright install --with-deps chromium
npm test
python3 -m pytest -q backend/tests/
FH_E2E_PYTHON=python3 npm run test:e2e
```

Windows PowerShell (Python 3.12+ и Node 24):
```powershell
npm ci
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-test.txt
npx playwright install chromium
$env:FH_E2E_PYTHON = (Resolve-Path .\.venv\Scripts\python.exe).Path
npm run test:e2e
```

Не используйте production-учётные записи. На CI сервер и SQLite создаются временно. Для локального отладочного запуска ожидается свободный порт 8791. `playwright.config.mjs` не переиспользует внешний сервер. Падения публикуют только снимки и trace с синтетическими данными, с хранением 7 дней.

## GitHub Actions и контроль слияния

Обязательные рабочие задания: `app-tests`, `email-auth-tests` и `e2e-real-browser`. Последнее использует `npm ci`, Python и реальный Chromium, без `continue-on-error`. Критический провал приводит к неуспешному заданию и статусу PR.

**Важное условие:** для фактического запрета слияния в настройках ветки `main` нужно включить branch protection/ruleset с обязательным `e2e-real-browser` (а также текущими unit/auth). Просто добавить workflow недостаточно. Проверять включённость политики отдельно перед закрытием #31. Доступность ручного merge без зелёных проверок означает, что требование не выполнено.

## Сохранность после обновления

`pwa.spec.mjs` использует штатный Service Worker и имитирует новую ревизию лишь **тестовым ответом** локального сервера, проверяет активацию нового CacheStorage и сохранность записей. Это доказывает сохранность в синтетическом цикле обновления, а **не** физическое обновление установленной iOS PWA между двумя production-коммитами. Перед релизом, меняющим схему, отдельно запускать сценарии с предыдущей собранной оболочкой и зашифрованной v1-копией (зависимость #32). Старые приложения других версий здесь не поставляются.

## Read-only production smoke и квитанция

После **разрешённого** релиза, в checkout с проверенным коммитом `main`:
```sh
node tests/e2e/production-smoke.mjs https://example.com 0123456789abcdef0123456789abcdef01234567
```

Скрипт делает только GET запросы к публичным статическим ресурсам и `/api/auth/email/config`, сравнивает SHA-256 ответов с конкретными файлами указанного коммита, не передаёт cookies, не создаёт аккаунты и **не трогает финансовые записи**. Дополнительно можно указать `--health=/healthz`, если этот маршрут реально предоставляется окружением. Неверная версия ресурса завершает проверку с кодом 1. Нет встроенной гарантии, что все ресурсы на сервере соответствуют указанному коммиту или что rollout/rollback выполнен: эти сведения нужно сверять с реальной квитанцией развёртывания и доступным rollback. Скрипт не развёртывает и не откатывает приложение.

Квитанция должна содержать: полный SHA `main`, URL и результаты CI для этого SHA, задеплоенный SHA/revision (по данным системы релиза), результаты read-only smoke, реальный механизм отката и его проверку, Safari-матрицу `PASS`/ `NOT_RUN`.

## Ограничения и дефекты

Внимание: проверяйте CDN-кэш: если HTML и Service Worker обновлены, но CSS возвращается из старого кэша, проверка должна завершаться FAIL. Не считайте корректной установку PWA, пока байты ресурсов не соответствуют релизу.

- Дефект горизонтальной прокрутки при ширине 320 px был выявлен E2E и исправлен отдельно в PR #52 (Issue #50). Совместная изолированная сборка #31 + #52: Chromium 14/14 PASS. Отдельный production CSS/UI по-прежнему запрещён в PR #49.
- Нельзя проверять реальную Cloudflare CAPTCHA в production через обход. В E2E тестируется только штатный backend с разрешённой тестовой подменой внешней проверки.
- Токены тестового подтверждения почты остаются только внутри локального процесса и синтетического браузера; их нельзя включать в логи, screenshot или внешнюю почту.
- Данные из одной изолированной копии/браузерного контекста не являются синхронизацией облачной финансовой базы. Миграции других версий относятся к #32.
