# Кредитное расчётное ядро (#39)

## Статус и обратная совместимость

Новое независимое ядро: `src/domain/loans/`. Прежние `finance.js`, `schedule.js`, `app.js`, `storage.js`, React-компоненты, IndexedDB, финансовые данные и шифрованные резервные копии **не изменены**. Никакая автоматическая миграция существующих кредитов не выполняется.

Это альтернативный набор правил, а не новая реализация с тождественным результатом старого `APR / 12`. Интеграция должна быть согласована отдельно с #33 и #72: изоляция фактических проводок, отсутствие двойного списания, соответствие новых сущностей договора и отсутствие изменений старой истории.

**Точность конкретного банка не подтверждена.** Совпадение синтетических эталонов по копейкам не доказывает банковскую идентичность: договор может задавать другой порядок округления, валютирование, перенос выходных/праздников, комиссии, штрафы, капитализацию или порядок перерасчёта.

## Переход от сохранённых кредитов v1/v2 без тихой миграции

Для старых записей `FinanceLoan` доступны `openingCents`, `paymentCents`, `apr`, `termMonths`, `dueDay`, `asOfDate` и опциональные импортированные строки. **Этого недостаточно** для определения ежедневных процентов и правил конкретного банка. Особенно нельзя без подтверждения превращать `apr` (число JavaScript) в миллионные доли процента, угадывать `firstDueDate` по `dueDay` или трактовать исходный остаток как чистый основной долг.

Чистый `prepareLegacyLoanPreview(legacyLoan, acceptedTerms)` возвращает `status:'needs-confirmation'` и список недостающих условий либо `status:'ready'` с отдельными `LoanTerms`. Готовность требует явного подтверждения договора, того, что `openingCents` является основным долгом без задолженности по процентам на `asOfDate`, даты первого платежа, **отдельно подтверждённого регулярного дня месяца (`dueDayAnchor`, 1-31)**, точной номинальной ставки (`annualRateMicroPercent`), `dayCount`, `rounding`, типа графика и выбора `installmentBasis`. Предварительный просмотр **не подтверждает банковскую точность** и не записывает результат в IndexedDB.

Режим `installmentBasis:'fixed-contractual'` использует сохранённый `paymentCents` только после подтверждения его договорного характера. `'recalculate'` находит новый размер математически, сохраняя прежний. Для дифференцированного графика обязателен `recalculate`. Горизонт ограничен первоначальным сроком: отсутствие полного погашения показывается как `complete:false`, а не скрыто продлевается.

**Важно:** `prepareLegacyLoanPreview` не конвертирует `LoanPayment`, не объявляет факты банковскими списаниями, не создаёт `PaymentLink` и не затрагивает `schedule`. Применение `LoanPayment` и реальное движение по счёту допустимы только после #33/#67/#68/#69 с явными идентификаторами и идемпотентными серверными проводками. Пока подтверждения нет, UI продолжает старый приблизительный расчёт и прежний импорт CSV.

## API и типы

`calculateLoan(terms, events, {mode, asOfDate?})` - чистый детерминированный расчёт; системные часы, сеть и хранилище не используются.

- `terms.principalCents` - положительный основной долг в целых копейках, максимум `1_000_000_000_000`.
- `startDate` - дата исходного остатка без начисленных ранее процентов. `firstDueDate` - первая дата платежа, позже даты начала не более чем на 366 дней.
- `termMonths` - договорный срок 1-1200 месяцев; `maxExtensionMonths` - горизонт просрочки после срока, по умолчанию до 240, при этом суммарно не более 1200 периодов.
- `annualRateMicroPercent` - целое число миллионных долей процента: 9,5% = `9_500_000`, 0,001% = `1_000`; диапазон 0-100%. Это *номинальная*, не эффективная ставка.
- `scheduleType: 'annuity' | 'differentiated'`; для аннуитета можно передать договорный `paymentCents`, иначе он подбирается двоичным поиском с учётом ежедневных процентов и округления.
- `rateChangePolicy: 'recalculate' | 'keep-payment'` управляет перерасчётом аннуитета при смене ставки (по умолчанию `recalculate`).
- Событие `payment-change` (поле `paymentCents`) задаёт новый договорный размер регулярного аннуитетного взноса без фактического списания; действует с указанной даты, в том числе в день взноса. В одной дате применяется после автоматического перерасчёта ставки, но до обычных и досрочных платежей. Ошибочную корректировку можно аннулировать через `voidedAt`. Для дифференцированного графика событие запрещено.
- `dueDateChangePolicy: 'keep-payment' | 'recalculate'` явно определяет поведение при изменении дня платежа: по умолчанию сохраняется рассчитанный размер взноса, при `recalculate` новый аннуитет подбирается **только для оставшихся ещё не оплаченных дат**. Размер прошлых взносов не пересчитывается. Если договор требует иного порядка, требуется отдельное правило модели.

Все даты - календарные строки `YYYY-MM-DD` без времени и временной зоны; разность считается в днях UTC. Начало процентного периода включительно, конец исключительно. Дата 2028-02-28 -> 2028-03-01 содержит **два дня**.

## Правила day-count

| Правило | Расчёт доли года |
| --- | --- |
| `ACT/365F` | Фактические календарные дни / 365 даже в високосном году |
| `ACT/360` | Фактические календарные дни / 360 |
| `ACT/ACT-ISDA` | Дни каждого календарного года делятся на 365 или 366 отдельно |
| `30E/360` | Европейский 30E/360; число 31 приравнивается к 30 |

Проценты = текущий основной долг (коп.) × номинальная годовая ставка × доля года. Вычисления ведутся с `BigInt` и общим точным целочисленным знаменателем. Округления `HALF_UP` и `HALF_EVEN` выбираются явно, результат целочисленный. Дробный остаток переносится между начислениями. Округление применяется при платеже и на очередную дату взноса, а не при каждом изменении календарного дня. Смена ставки действует **начиная с даты события**; до неё применяется предыдущая ставка.

Плановые даты создаются по исходному дню месяца: 31 января -> 28/29 февраля -> 31 марта. Изменение `due-date-change` вступает в силу **только со следующего календарного месяца** и не сдвигает уже назначенный день текущего месяца. Для договоров с платежом, например, 31-го числа, когда первый выбранный месяц - февраль, можно явно задать `dueDayAnchor:31` при `firstDueDate:'2026-02-28'`: последующие даты будут 31 марта и 30 апреля. Без `dueDayAnchor` прежнее поведение для всех существующих вызовов сохраняется - якорь равен числу `firstDueDate`. **Не получать месячный якорь автоматически из legacy `dueDay` без подтверждения договорного графика.**

Первоначальный аннуитет рассчитывается по исходным договорным датам без будущих событий. Новые даты применяются в хронологическом порядке; при выборе `dueDateChangePolicy:'recalculate'` пересчёт не меняет суммы уже закрытых или наступивших взносов. Будущие переносы не попадают в фактический снимок до их даты события.

## Фактические платежи и прогноз

- `mode:'plan'`: плановые платежи моделируются в срок, а события фактических оплат игнорируются. Это математический сценарий, а не подтверждение перевода денег.
- `mode:'actual'`: применяются только события оплаты с датой не позже `asOfDate`; очередная дата взноса сама **не списывает** деньги. Пропуск увеличивает только невыплаченные проценты, без автоматической капитализации, пени и штрафов.
- `mode:'forecast'`: реальные платежи до `asOfDate` воспроизводятся, последующие даты считаются гипотетическими. При незакрытом фактическом периоде `actualOpenPeriod` хранит выплаты между последней датой взноса и `asOfDate` отдельно от сумм будущих взносов.
- Проценты гасятся перед основным долгом. Частичные платежи разрешены; нулевой, отрицательный или превышающий сумму долга фактический платёж отклоняется. При полном погашении выдаётся дата `paidOffDate`; если за заданный горизонт погашение невозможно, `complete:false` и дата `null`. Полное фактическое погашение в дату платежа сохраняется как последняя строка графика; досрочное закрытие **между** датами платежей сохраняется в `paidOffDate` и `actualOpenPeriod` без фиктивного переноса на следующую дату.
- `paymentKind:'extra'` с `strategy:'shorten-term'` сохраняет текущую сумму взноса и может сократить срок; `strategy:'reduce-payment'` рассчитывает меньший взнос на оставшиеся первоначальные даты. Без стратегии используется `shorten-term`.
- Дифференцированный график: равная, с поправкой на последнюю копейку, доля основного долга плюс начисленные и невыплаченные проценты; при досрочном погашении можно уменьшить ежемесячную долю либо сократить срок.

Журнал событий имеет уникальные `id`, дату и тип. Чтобы отменить ошибочную операцию, исходный объект сохраняют с `voidedAt` и заново рассчитывают график. Внутри даты сначала применяется новая ставка, затем обычные платежи, затем досрочные; при совпадении категорий используется сортировка по `id`. Два активных изменения ставки на одну дату и два изменения дня в одном месяце запрещены. Повторный вызов с одинаковыми входными данными должен возвращать идентичный результат.

## Сверка с банковским CSV

`reconcileLoanSchedule(calculatedRowsOrResult, importedRows)` принимает массив строк или полный `LoanResult` нового ядра и банковские строки в форме, возвращаемой уже существующим `parseSchedule()`. Для досрочного закрытия между платежами **передавать полный `LoanResult`**, чтобы отдельно сравнивать `paidOffDate`: массив плановых строк сам по себе не содержит дату внеочередного погашения. Сравнивает по **порядковому номеру взноса**, а не по догадке о банковском календаре. Возвращает `calculated - imported`: разницу дат в днях, суммы взноса, процентов, тела кредита и остатка в копейках; отдельно сравнивает дату полного закрытия. Отсутствующая колонка `interestCents` или `principalCents` - значение `null`, а не ноль. `matchingKnownFields=true` означает совпадение имеющихся столбцов, **не** банковскую точность. Только `comparisonComplete=true` подтверждает наличие всех полей сверки; `exactMatch=true` дополнительно требует нулевых расхождений, подтверждённых дат полного закрытия и всех полей.

Проверяются реальные календарные даты, возрастающий порядок и неотрицательные целые копейки. Разность между банковским платежом и суммой его процентов/основного долга **не приводит к отказу в импорте**: она возвращается как `bankUnallocatedCents` (например, для комиссии или страхования). Эта сумма не засчитывается автоматически как проценты или тело кредита. Расхождение не исправляется автоматически: оно сигнализирует о необходимости проверить договорные параметры, дополнительные начисления, дату валютирования и правила банка.

## Read-only модель сверки для будущего пользовательского экрана

`prepareReadOnlyLoanComparison(snapshot, approvedRules, fullBankRows)` объединяет уже утверждённые правила из `prepareLegacyLoanPreview()`, плановый расчёт `calculateLoan()` и построчную сверку `reconcileLoanSchedule()`. Функция выполняется без сети, IndexedDB, банковских API и без изменений старых кредитов.

- `needs-confirmation`: существенные условия банка отсутствуют; никакой расчёт или сверка не выдаются.
- `no-bank-schedule`: есть подтверждённый **гипотетический план**, но нет полного импортированного графика.
- `incomplete-bank-evidence`: известные колонки совпали, но отсутствует полная разбивка или подтверждение даты закрытия.
- `numerical-match`: все сравниваемые поля и дата закрытия сошлись по копейкам **только при выбранной математической модели**.
- `differences`: конкретные расхождения по датам, платежам, процентам, телу или остатку.

Независимо от статуса `bankParityVerified:false`. Нельзя объявлять данные точными для конкретного банка без независимой проверки договора. Нельзя передавать в эту функцию сокращённый до четырёх строк массив, который показывает прежний React-экран: для сверки нужен **полный** `loan.schedule` из уже локально загруженного CSV. `LoanPayment` намеренно не переводятся в события ядра: будущий серверный контракт #33/#67 должен связывать каждый подтверждённый факт с ровно одной денежной проводкой. Нет автоматической миграции или сохранения утверждённых правил в финансовое хранилище.

## Локальная сверка эталонного банковского CSV (без передачи файлов)

Для обезличенной приёмки можно выполнить **только на своём компьютере**:

```bash
node scripts/compare-bank-loan.mjs ./private-data/loan-contract.json ./private-data/bank-schedule.csv --json --details
```

Формат `loan-contract.json` (полностью синтетический пример, не реальный договор):

```json
{
  "schemaVersion": 1,
  "terms": {
    "principalCents": 1000000,
    "startDate": "2026-01-01",
    "firstDueDate": "2026-02-01",
    "termMonths": 2,
    "annualRateMicroPercent": 12000000,
    "dayCount": "ACT/365F",
    "rounding": "HALF_UP",
    "scheduleType": "annuity",
    "maxExtensionMonths": 0
  },
  "events": [],
  "options": { "mode": "plan" }
}
```

Папка `private-data/` уже исключена из Git через `.gitignore`. Создавайте её на своём устройстве, не сохраняйте реальные файлы в публичной ветке или в протоколах CI.

CSV использует уже существующие заголовки `Дата;Платёж;Проценты;Основной долг;Остаток`, либо английские аналоги. По умолчанию `options.mode='plan'`; режимы `actual` и `forecast` требуют `asOfDate`. В режиме `plan` фактические оплаты **не воспроизводятся** (выводится `factualPaymentsIgnored`), поэтому банковские фактические движения нужно анализировать отдельно.

Команда возвращает только агрегированные показатели. С флагом `--details` выводятся **номера строк и арифметические разницы**, без исходных строк CSV, дат, идентификаторов и названий файлов. `--json` выдаёт ту же сводку в JSON. Код выхода: **0** - полный числовой матч по представленным колонкам и дате закрытия; **2** - расхождения или недостаточная полнота данных; **1** - неверный локальный ввод. `arithmeticExactMatch=true` не означает соответствие конкретному банку: `bankParityVerified` остаётся `false`.

Договор и CSV остаются в локальной файловой системе: скрипт читает их только из выбранных путей, не записывает результаты в файлы и не обращается к сети. Не коммитить и не отправлять банковский CSV в GitHub Actions/Issues или публичный репозиторий. Для реальной приёмки нужны **согласованные обезличенные** исходные параметры, начисления и графики, с явно выбранным day-count, правилами округления, датой валютирования и комиссией.

## Проверка и ограничения внедрения

Автоматизированные синтетические эталоны: нулевая и переменная ставка, ACT-конвенции, переход года и 29 февраля, досрочное и полное погашение, два варианта пересчёта, частичный и пропущенный платёж, отмена, ошибки входа, воспроизводимость и сверка графиков. Эталонные данные без персональной информации.

Проверка производительности выполнена отдельно на изолированной среде; реальная скорость браузера, E2E и банковская идентичность этим не устанавливаются. До подтверждения #33 и #72 **не подключать** эту модель к интерфейсу и не объявлять прежние графики точными. Для старых кредитов без указанного day-count не назначать молча `ACT/365F` - явно предлагать пользователю выбор и сохранять старый режим по умолчанию.


## Пакетная локальная сверка независимых банковских графиков

Для приёмки по #39 можно сверять 2-12 отдельных, утверждённых владельцем обезличенных графиков. Исходные договоры, суммы и банковские CSV остаются на локальном устройстве; никакого импорта в IndexedDB, сетевых запросов или сохранения выходных файлов нет.

Создайте закрытый манифест private-data/approved-references.json рядом с папками reference-1 и reference-2 (папка private-data уже исключена из Git). Содержимое манифеста:

    {
      "schemaVersion": 1,
      "cases": [
        {
          "approvedForLocalAcceptance": true,
          "contractFile": "reference-1/contract.json",
          "bankCsvFile": "reference-1/bank.csv"
        },
        {
          "approvedForLocalAcceptance": true,
          "contractFile": "reference-2/contract.json",
          "bankCsvFile": "reference-2/bank.csv"
        }
      ]
    }

Каждый contract.json использует schemaVersion 1 и формат условий из предыдущего раздела. Указывайте только относительные пути внутри каталога манифеста. Повторяющиеся файлы и идентичное содержимое графиков отклоняются. Поле approvedForLocalAcceptance - заявление владельца о пригодности исходных данных, а не независимая верификация банка.

Запуск (Node.js 24):

    node scripts/verify-bank-loan-references.mjs private-data/approved-references.json

В ответе только агрегированное количество графиков, полных числовых совпадений, неполных данных и несовпадений; ни отдельные суммы, ни даты, ни пути, ни личные данные не печатаются. Код завершения 0 - все графики полностью совпали по заданной модели и известным колонкам, 2 - есть расхождение/неполнота, 1 - неверные приватные входные данные. Даже при коде 0 поле bankParityVerified остаётся false: подтверждение правил договора и независимого происхождения графиков - отдельный этап. Синтетические тесты не заменяют два-три независимых обезличенных банковских эталона.
