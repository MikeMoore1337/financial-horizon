# Financial Horizon #34 - approved local unlock behavior (2026-11-08)

**Owner approval:** the unlock/recovery **interaction scenario** was explicitly confirmed in the project conversation on 2026-11-08 and recorded in [Issue #34](https://github.com/MikeMoore1337/financial-horizon/issues/34#issuecomment-6718670579). This is **not** approval to delete legacy financial records, turn on an existing-user migration, publish a visual design, or claim end-to-end encryption. The visual layout remains subject to the repository's visual review policy.

## User flow contract

1. On explicit local-encryption setup for one verified account or a guest namespace, the user chooses a **local** passphrase (12-1024 characters), which is different from and not derived from their login password or session cookie. A failed setup leaves all original data intact.
2. After the encrypted keyset and candidate snapshot have been durably committed and verified, show the independent 256-bit recovery key **once**. The user acknowledges storing it outside this browser/device. Do not persist the plaintext recovery key, passphrase, or raw DEK.
3. A returning user must explicitly unlock that particular account/guest scope with their local passphrase or recovery key. A recovery key can be used to rewrap the passphrase. A server-side password reset does not decrypt local data; when both local credentials are gone, recovery of that encrypted copy cannot be promised.
4. Manual lock, logout, **even a same-account re-selection**, account switch and session revocation invalidate all active and pending local-crypto operations. The integration must also clear financial React/legacy state, DOM history, cached data and stop the outgoing sync queue. A cleared server session alone cannot be treated as proof that the UI has cleared sensitive data.
5. Offline unlock is allowed only for an already-prepared local scope with persisted ciphertext and keyset. It does not provide server authorization or permission to sync financial changes.
6. Migration additionally requires a verified *separately saved* encrypted backup, confirmation of the target scope and independent opt-in. No plaintext legacy deletion or active-store cutover is permitted without post-migration restore and rollback validation and **separate explicit consent**.

## Code boundary (stage 3: independent controller)

`src/security/local-budget-session.ts` implements a **non-persistent** controller around `unlockLocalKeyset`:

- Host must select a validated scope using `selectScope` after checking the real authenticated user or explicitly choosing guest. This class is **not** an authorization provider.
- `state` is `unselected`, `locked` or `unlocked`. `unlock` stores an unextractable `LocalVault` only in memory. It never reads `localStorage`, auth cookies, IndexedDB, or network services.
- `lock` destroys the vault reference, and `logout` also drops the selected scope. A generation counter invalidates any in-flight or competing unlock/encrypt/decrypt completion. The host must call these methods on every relevant lifecycle event; this module does **not** wire itself into the UI yet.
- The underlying `LocalVault` performs authenticated encryption and decryption; the controller prevents stale completion delivery after a local lock, and refuses keysets belonging to a different scope.
- A browser restart constructs a fresh locked session. The existing stage-2 storage module can supply a keyset and sealed snapshot after explicit scope selection; no auto-unlock is allowed.

## Remaining security gates

**Not implemented:** live UI screen, full logout/DOM cleanup wiring, cross-tab revocation, idle-lock scheduling, pause-and-resume of offline sync, coordinated migration journal, atomic active-store cutover, safe deletion of legacy plaintext, post-cutover rollback with pending mutations and physical device acceptance.

#33 (accounts domain), #66 (PostgreSQL) and #68 (offline sync) contracts must be validated before integration touches `storage.js`, `state-migrations.ts`, React screens, backup APIs, Service Worker or the production finance API. Neither these isolated modules nor a successful CI run protects existing plaintext IndexedDB records; Issue #34 stays open until a verified, consented production migration and restore drill. Browser/PWA cannot guarantee secure deletion of historical plaintext from caches, filesystem snapshots or flash storage.


## Recovery-secret reissue when the old recovery key was lost (inert stage)

The local passphrase and the one-time recovery secret protect the **same random DEK**, but via independent wrappers. Losing the *recovery key alone* does not mean the protected records are unrecoverable as long as the owner still knows the local passphrase. A browser crash **after** an encrypted keyset is committed but **before** the one-time recovery secret is displayed also requires a recovery-reissue path.

`rotateLocalRecoveryKey(keyset, localPassphrase, expectedScope)` provides a pure, keyset-only rewrap. `rotateAtomicEncryptedRecoveryKey(scope, unlockedSession, localPassphrase)` additionally commits it in **one native IndexedDB readwrite transaction**, after comparing the entire previous keyset and epoch against current values under the database write lock. Neither path re-encrypts/rewrites the financial snapshot, pending outbox or conflict inbox; the DEK, scope and keyId remain unchanged. An incorrect passphrase, stale writer or aborted IDB transaction cannot invalidate the prior recovery secret. **If manual lock, logout or account switch occurs while the native keyset transaction is still active, the captured lifecycle AbortSignal causes an immediate `tx.abort()` before commit**, keeping the old recovery secret valid. If the IDB transaction has **already committed** when the session is revoked, JavaScript cannot roll back the new keyset atomically; the new secret may not be returned, but the unchanged local passphrase still allows another rotation. The UI must clearly explain this exceptional recovery path and must never treat a revoked account as authorized to display the newly issued secret. On success the previous recovery key no longer unlocks the **current persisted keyset**; the new independently generated 256-bit secret must be displayed **once**, copied outside the browser and confirmed saved. Neither the local passphrase nor the recovery key is stored as plaintext in IndexedDB, localStorage, source code or logs.

**Safety requirement:** Recovery-key rotation requires the **local passphrase**, not merely the old recovery key. If the browser closes between the successful keyset commit and displaying the new recovery secret, the user can still unlock using that passphrase and generate another recovery secret. If the passphrase is lost but the old recovery key is available, first use the existing `changeLocalPassphrase` workflow to set a new passphrase, then reissue recovery. If **both** passphrase and recovery key are lost, the encrypted copy cannot be recovered cryptographically. A server login/password reset is never a substitute.

The rotation code is independent and **not imported by the active application**. This stage does not approve or perform migration, cutover or deletion of legacy plaintext data. A future approved UI must explicitly show the one-time secret and obtain confirmation that it was saved externally, and explain that the previous recovery key no longer opens the **current keyset**, without promising revocation of historical copies. Browser/OS memory zeroization of immutable strings cannot be guaranteed by JavaScript.


### Important: reissue is NOT cryptographic revocation of exposed credentials

The reissue operation keeps the **same DEK and the same ciphertext**. It updates only one wrapping slot in the currently stored keyset. If an attacker already possesses **both** an older copy of the keyset (for example, from a profile snapshot or backup) **and** the previous recovery secret, that copy can still unwrap the unchanged DEK and decrypt ciphertext available to the attacker, including newer records encrypted with that DEK. Updating IndexedDB cannot revoke old offline copies, and no claim of universal old-key invalidation, device-compromise mitigation, or secure erasure is justified.

This API is intended for a **lost but not suspected-compromised** recovery secret. A suspected disclosure requires a separately designed and approved **new DEK with authenticated re-encryption of all live snapshot/outbox/conflicts**, handling of historical backups, crash-safe migration/rollback, cross-tab fencing, explicit per-scope consent and verified restoration. That workflow is **not implemented or authorized** by this inert stage. The eventual UI must clearly distinguish lost-secret reissue from compromised-secret recovery, and must not describe the former as a security breach reset.

## Stage 9: passive legacy writer guard (NOT a cutover)

The running `storage.js` now checks the reserved `encrypted-cutover-fence-v1:<state-key>` entry in its existing `financial-horizon-browser-v1` / `finance` store in the **same native IndexedDB transaction** as a read, update, v1-to-v2 rewrite or verified-account claim. Any present marker blocks those operations for that selected scope, before returning plaintext to the caller. Other account/guest scopes remain independent. The application **does not create this marker**, activate encryption, migrate financial data, delete legacy values or change sync. With no marker, existing local-first behavior remains unchanged.

**This is not complete cross-tab fencing:** older cached JavaScript does not check the marker and may still write. Before any future marker creation the migration coordinator must verify that all prior tabs/writers are quiesced, persist a crash-safe activation/rollback journal, reconcile outbox and cloud #68, confirm an independently restored external encrypted backup, obtain per-scope user consent and provide verified recovery. No production marker is authorized by this preparatory change. Do not clear a marker to bypass a failed migration; an independently verified rollback must restore the correct source. This guard does not encrypt or erase existing plaintext.

## Stage 10: legacy account-selection lifecycle revocation (not live encryption)

The active `storage.js` now synchronously revokes the previously selected guest/account storage key at the **start** of each `selectStateScope`, before opening IndexedDB or validating the replacement identity. Failed identity validation, a fenced target, an IndexedDB error, or an overlapping account selection leaves the adapter **unselected**, not pointing back to the former user's budget. `readState` and `updateState` require the currently selected generation; they fail closed after any scope change rather than returning stale finance payloads. Their native IndexedDB transactions subscribe to an `AbortSignal` revoked by the next selection, aborting in-flight readwrite transactions before commit when still active. If a transaction committed before a switch, that prior transaction cannot be undone; only future results/access are denied.

This is **same-tab legacy state isolation**, not cross-tab fencing, an authorization provider, or a cryptographic `LocalBudgetSession`. It does not persist keys, activate the encrypted source, change the approved unlock UX, perform migration, delete plaintext, or stop older cached clients. The application host must still clear its displayed/React finance state and close dialogs on auth/logout/session revocation; a stale tab may remain dangerous until the separately coordinated #68 writer protocol is installed and validated. A failed scope selection requires a fresh verified selection before any further financial read/write.
