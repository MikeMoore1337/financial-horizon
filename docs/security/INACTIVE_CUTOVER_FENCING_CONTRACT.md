## 1. Неподвижные границы безопасности

- Для гостя и авторизованного `userId` используются разные, строго проверенные `scope`. Идентификатор аккаунта получается из проверенной сессии, никогда из резервной копии, `localStorage` или URL. Нельзя показывать или отправлять очередь другого аккаунта.
- `LocalBudgetSession` удерживает DEK только в памяти; logout, account switch и ручная блокировка отменяют локальные операции, уничтожают ссылки на расшифрованные данные/DOM и блокируют исходящий транспорт. Наличие офлайн-фразы не подтверждает серверную сессию.
- Нельзя назвать старый IndexedDB зашифрованным. Ни резервная копия, ни encrypted candidate сами по себе не блокируют работающий `storage.js`.
- До отдельного подтверждения владельца нужны утверждённый **визуальный** макет, проверенный на другом устройстве/вне браузера зашифрованный backup *конкретного scope*, демонстрация restore, согласие на cutover, rollback-drill. Удаление старого plaintext - **отдельное** разрешение после приёмки; гарантировать физическое стирание flash/снимков браузера невозможно.
- Не использовать автоматический fallback из зашифрованного источника в legacy при ошибке ключа, тега AES-GCM, scope, версии или журнала: это может открыть устаревшую или чужую финансовую запись. Требуется изолированный экран восстановления.
- Отдельный серверный `If-Match`, `profile_revision`, `client_mutation_id` и локальный `epoch` имеют разные значения; один нельзя использовать вместо другого. Ни Web Locks, ни BroadcastChannel не предоставляют авторитетного server ACK.

## 2. Контракт будущего fence для ВСЕХ писателей

`Web Locks` и `BroadcastChannel` применяются только для координации; безопасность должна зависеть от **долговременной монотонной версии записи (fence epoch)**, которую каждый писатель сверяет внутри той же native IndexedDB readwrite-транзакции, что и запись финансов/очереди. Смена `scope`, logout, lock, отзыв сессии, смена `fence epoch` или schema gate должны синхронно запрещать новые записи. Вкладка с устаревшей lease не может зафиксировать запись после выдачи нового токена. Краткоживущий lease без проверки epoch при commit **недостаточен**.

**Ключевой стоп-фактор:** текущий `storage.js`, открытая старая вкладка и кэшированная версия PWA не обязаны проверять новый fence. BroadcastChannel не доказывает, что все возможные вкладки ответили. До обновления всех активных писателей, доказанной блокировки старых версий и тестирования на реальных старых сборках cutover запрещён. При неизвестном/неподтверждённом старом writer - `NO_GO`, а не таймаут с принудительным переключением.

## 3. Предлагаемый долговременный журнал переключения (не реализован)

Состояние журнала должно храниться **вне** временной памяти JS, быть привязано к `scope` и иметь проверяемую версию; его место хранения и атомарные операции утверждаются совместно с #68. Нельзя предполагать одну ACID-транзакцию для двух отдельных IndexedDB или IndexedDB и PostgreSQL.

| Состояние | Условие перехода и правило после сбоя |
| --- | --- |
| `LEGACY_ACTIVE` | По умолчанию рабочий источник - старый. Никакого автоматического перехода от обнаружения encrypted candidate. |
| `FENCING` | Явное согласие, подтверждение личности, recovery и внешнего backup; все совместимые писатели остановлены, источник и outbox зафиксированы точным revision/hash/epoch. При сбое исходная копия не меняется; несовместимые писатели - NO_GO. |
| `CANDIDATE_VERIFIED` | Отдельно записанный зашифрованный snapshot+outbox+conflicts прочитан новой сессией и побитово/семантически сверён с замороженным источником; вся очередь (включая sending/conflict) перенесена с теми же идентификаторами, порядком и статусами. При расхождении оставить оба источника, ничего не удалять. |
| `ACTIVATION_INTENT` | Долговечная квитанция о внешнем backup, `scope`, `sourceRevision`, `fenceEpoch`, `candidateEpoch/keyId`, digest очереди, идентификатор попытки и решение пользователя. Никаких паролей, ключей, сумм или названий операций в журнале/логах. Intent сам по себе не назначает новый источник. |
| `PROTECTED_ACTIVE` | Защищённый источник выбирается только после проверки сохранённой квитанции, доступности keyset/bundle, соответствия scope и fence и повторного восстановления. Маркер выбора источника коммитится долговечно отдельным атомарным действием; при перезапуске выбор восстанавливается **по верифицированному маркеру**, не по наличию базы. |
| `RECOVERY_HOLD` | Несогласованный журнал, stale writer, потерянная вкладка, неверный ключ, checksum, ACK или частичный commit - блокировка записей и выдача пути восстановления; не выполнять скрытый auto-rollback в plaintext. |
| `ROLLBACK_GUARDED` | До новых защищённых мутаций можно вернуть ранее подтверждённый legacy только после повторной сверки source/outbox. После хотя бы одной защищённой правки, отправки или получения серверного ACK нельзя переключаться на старый snapshot: сохранение защищённой очереди и её подтверждение/восстановление обязательны. |

Для состояния и журналируемых переходов нужен монотонный `generation` и CAS, так чтобы две вкладки не могли одновременно считать себя владельцем миграции. Маркер `PROTECTED_ACTIVE` не должен существовать раньше проверяемой независимой копии. Не использовать `localStorage` как источник истины выбора. При сбое между записью зашифрованного bundle и commit marker допускается **только** восстановление статуса по журналу и повторная проверка, не догадка на основе наличия `bundles[scope]`.

## 4. Сохранение офлайн-очереди и серверная идемпотентность

- Каждый локальный command UUID и payload с `base_revision`, `If-Match`, профилем и fingerprint записываются **атомарно** с локальным optimistic overlay. Ретрай при timeout/сбое повторяет **тот же** идентификатор, тело и предусловия. Новое тело со старым UUID запрещено.
- Сервер #67 в **одной PostgreSQL-транзакции** проверяет право, dedup/fingerprint **до** stale revision, блокирует профиль, фиксирует ledger postings, команду, change log, revision и стабильную idempotency receipt. Один и тот же ключ+fingerprint даёт тот же результат без повтора операции; другой fingerprint = 409. `If-Match` stale = 412, отсутствие = 428, семантический конфликт = 409.
- Клиент помечает команду подтверждённой/удаляет из pending **только в одной локальной защищённой IDB-транзакции с применением подтверждённой server delta, cursor/revision и fence/scope check**. После HTTP 200, но до локального commit, она остаётся pending: при повторе сервер возвращает сохранённую квитанцию, деньги не списываются дважды.
- При HTTP 401/logout запретить дальнейший flush и очистить RAM, **но не удалять** durable pending, sending или conflict entries. Для другого `userId` эта очередь невидима и не отправляется; прежний аккаунт может возобновить после собственной аутентификации и локальной разблокировки.
- При rollback/аварии ни одна `pending/sending/conflict` операция не может быть молча потеряна. Если нет возможности доказать их перенос в другую схему с теми же UUID и квитанциями, состояние `RECOVERY_HOLD` и запрет автоматического переключения.

## 5. Минимальная обязательная матрица независимой проверки

Тестировать синтетические финансы, реальные native IndexedDB/Web Crypto, Chromium + WebKit; физический iPhone/Safari - отдельный **NOT_RUN** до проверки на устройстве. Для серверных проверок #67/#70 - настоящая изолированная PostgreSQL с RLS, а не mock.

1. Две вкладки читают один epoch; обе пытаются записать разные pending-команды; ровно один CAS commit, другая получает конфликт и сохраняет свою команду для осознанного retry.
2. После freeze открыть старую вкладку/PWA со старым cached bundle и попытаться писать - fail closed **до commit**. Если old writer не участвует в fence, cutover NO_GO.
3. Logout/account switch между encrypt и IDB write, между put и oncomplete, после commit до выдачи receipt; ни одна вкладка не раскрывает чужой scope, recovery и pending сохранены.
4. Прервать процесс в **каждом** состоянии журнала, включая границу двух IndexedDB; после перезапуска нет скрытой активации, нет потерянных записей/очередей.
5. Timeout после успешного серверного commit и до HTTP ACK; повтор исходного UUID не создаёт второй ledger posting.
6. HTTP ACK получен, но локальная транзакция cursor+outbox откатывается; pending не удалён, повтор безопасен.
7. 401/отзыв сессии, затем другой `userId` на том же устройстве: прежний outbox ни виден, ни отправляется.
8. Ошибка KDF/неверная фраза, повреждение AES-GCM tag, keyset rollback, wrong schema, stale snapshot, mismatch backup - fail closed без plaintext fallback и удаления.
9. Offline/restart/новая вкладка с уже подготовленным scope: явное unlock; отсутствие сети не вызывает серверной отправки.
10. Восстановление внешнего encrypted backup **в отдельном браузере/устройстве**, контроль сумм/ID/дат/очереди и возможности чтения; фиксация фактического SHA приложения и результата.
11. Rollback **до** новых защищённых операций и **после** pending/ACK отдельно: второй случай не должен подменять новое состояние старым plaintext.
12. Production smoke и crash/browser restore на точном deployed SHA с доказанным переключателем OFF по умолчанию, независимым review, мониторингом и согласованным планом отката; проверка физического iOS PWA отдельна от WebKit CI.
