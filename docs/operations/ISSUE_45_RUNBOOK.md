# Financial Horizon #45 - SRE-проверки, нагрузка и восстановление

Статус: **AUTONOMOUS_TOOLING_ONLY / PRODUCTION_NO_GO**. Точка отсчёта: `main` `86bdcc09a507d8dd0d36a249974ab21c6fee7702` (2026-11-08). Архитектура: #65. Зависимости: #66 (PR #79), #67 и независимая приёмка #70. Отсутствие dev не даёт права нагружать или ломать production. Всё ниже запускается **только с синтетическими аккаунтами и данными на отдельном disposable PostgreSQL/API**; production допускает только согласованные read-only пробы.

## Безопасность и границы

- `ops/load/api_load.py` разрешает только явный `http://localhost:<port>` или loopback-адрес. Режим `replay` дополнительно требует `--ack-isolated` и `FH45_ISOLATED_DB=YES`. **Нельзя** перенаправлять localhost на production через туннель/прокси. Никогда не указывать production cookie, базу или реальный финансовый объект. Режим `read` тоже только для изолированной среды. Ограничения: 2-500 запросов, 2-16 потоков, timeout 0.2-10 с, задержка между пачками 0-5000 мс. Для нагружения выше этого уровня нужен отдельный согласованный план и резерв ресурсов.
- `ops/load/postgres_contention.py` работает только с PostgreSQL на loopback в специально созданной БД `fh_ops45_*`, в которую **не** переносились production записи; нужен `FH45_ISOLATED_DB=YES`. Две конкурентные операции проверяют свой тестовый ledger и receipts, не SQL бизнес-модели #66. Тест создаёт уникальную схему `ops45_<uuid>` и удаляет только её. Перед проверкой изолированной БД следует использовать не prod/tunnel и отдельную тестовую роль.
- `ops/observability/backup_guard.py` **только для зашифрованных архивов #66**. `run` вызывает штатные `backup.sh` и `offsite-upload.sh`, и только после успешного exit 0 и строки `OFFSITE_BACKUP_PASS` атомарно пишет локальную квитанцию; `verify` сверяет свежесть, SHA-256 и права на файл. Это не самостоятельная криптографическая проверка содержимого и не доказательство сегодняшней доступности offsite: нужен **независимый restore drill**. Квитанция должна храниться вне git, с правами 0600 в каталоге 0700. НЕ переносить в публичный CI и Issue файлы backup, DSN, приватные отчёты и пути.
- `ops/observability/metrics.py` считывает Linux `/proc`, `statvfs`, опционально `pg_stat_activity` через ограниченное подключение из `FH45_MONITOR_PG_DSN`, без записи финансов. Доступ должен даваться только read-only роли с правами на обезличенные счётчики. Измерения CPU/RAM относятся к Linux host/namespace, а не автоматически к конкретному контейнеру; для cgroup лимитов потребуется отдельная телеметрия. `health` обращается GET только к `/healthz` и `/readyz` и не читает тело ответа. Маршруты должны быть реализованы и приняты в #67; до этого 404 означает NOT_READY, а не PASS.
- Любой отчёт содержит только коды статуса, агрегаты, латентность и метки сценариев. Запрещены параметры URL, финансовые суммы, идентификаторы, email, cookie, текст исключений PostgreSQL/SMTP и сырые HTTP-тела.

## Запуск автономных проверок (Python 3.12+)

```bash
python -m unittest discover -s ops/load -p 'test_*.py' -v
python -m unittest discover -s ops/observability -p 'test_*.py' -v
python -m compileall -q ops/load ops/observability
python ops/observability/metrics.py sample --mount /tmp
```

Для реальной БД требуется psycopg 3 из `backend/requirements-finance.txt` PR #79. В изолированной PostgreSQL создайте отдельную пустую БД `fh_ops45_ci`; не копируйте production-дамп и не включайте внешние порты. В секретном окружении тестового процесса (не в shell history или CI artifact) задайте `FH45_PG_DSN` и `FH45_ISOLATED_DB=YES`. Затем:

```bash
python ops/load/postgres_contention.py
```

Для API поднимите **копию #67** с отдельной пустой PostgreSQL и SQLite, а также заведите двух синтетических пользователей через штатный тестовый setup (без SMTP в production). Установите два разных краткоживущих значения `FH45_SESSION_A` и `FH45_SESSION_B` только в окружении локального процесса. Эти переменные содержат **значение cookie**, без `fh_email_session=`. Реальное истечение cookie нужно проверять отдельным `FH45_EXPIRED_SESSION`, а не произвольной несуществующей строкой. Сценарии:

```bash
python ops/load/api_load.py --origin http://127.0.0.1:8000 --mode read --workers 4 --requests 100
FH45_ISOLATED_DB=YES python ops/load/api_load.py --origin http://127.0.0.1:8000 --mode replay --ack-isolated
python ops/load/api_load.py --origin http://127.0.0.1:8000 --mode expiry
```

`read` измеряет двух авторизованных пользователей. `replay` намеренно создаёт одно синтетическое обязательство, параллельно повторяет **тот же** UUID/If-Match, требует `201+200` и ровно одно увеличение ревизии; затем отправляет **новую** команду с устаревшим ETag, требует `412`, а у второго пользователя проверяет неизменную ревизию. Эти ожидания основаны на контракте ADR-0065; при изменении API нужно отдельно согласовать контракт, не ослаблять проверку без основания. Результат - только JSON с p50/p95/p99, RPS, кодами ответов и gate. Команды, финансовые значения и приватные ответы не выводятся. При ошибках требуется диагностировать проблему внутри изолированного контура без копирования реальных данных в CI.

## Контроль backup и восстановление

Не менять `deploy/postgres/` в #45. После фактического ввода #66 можно интегрировать наблюдаемость, заменив команду запуска backup на **одобренную** обёртку, вызывающую исходные скрипты #66, не дублируя их в проекте:

```bash
python ops/observability/backup_guard.py run \
  --backup-dir /var/backups/financial-horizon-finance \
  --receipt /var/lib/financial-horizon/observability/backup-status.json \
  --backup-script /path/to/deploy/postgres/scripts/backup.sh \
  --offsite-script /path/to/deploy/postgres/scripts/offsite-upload.sh
python ops/observability/backup_guard.py verify \
  --backup-dir /var/backups/financial-horizon-finance \
  --receipt /var/lib/financial-horizon/observability/backup-status.json \
  --max-age-hours 8
```

Каталоги заранее создать с правами `0700`; file receipt будет `0600`. Примерные пути выше - шаблоны, **не утверждение о размещении на VPS**. Следует проверить, что `systemd` таймер **один**, не запускает старый backup параллельно новой обёртке; существующий `flock` #66 должен оставаться. При сбое `backup`, `offsite` или SHA проверка возвращает ненулевой код и НЕ создаёт ложную свежую квитанцию. Оповещать через `systemd` `OnFailure`/локальный администраторский канал, без прикрепления путей, email или stdout PostgreSQL. Отдельно контролировать отказ канала уведомления.

**Обязательная восстановительная проба после интеграции #66:** из нового полностью синтетического PostgreSQL сделать зашифрованную копию и проверить `deploy/postgres/scripts/restore-drill.sh BACKUP.gpg` в контейнере `--network none`. В исходном #79 проверяются 15 FORCE RLS таблиц, владельцы, ACL и `pg_amcheck`. На **чистом независимом кластере** дополнительно проверить авторизацию runtime, ALEMBIC upgrade, финансовые инварианты и сверку числа записей/хэшей синтетических наборов. Отдельно восстановить auth SQLite из консистентной копии (`sqlite3 .backup`, с WAL учётом) и проверить сессии. Нельзя импортировать production дампы в публичный CI. Повторить restore на **обрезанном** синтетическом `.gpg` архиве: `gpg`/`pg_restore` должны завершиться ошибкой, результат не должен быть опубликован как PASS. Для drill использовать короткоживущие ключи GPG и полный cleanup изолированных контейнеров. Время засекать от начала восстановления до **реального успешного API smoke**.

**Не выполнять отказ диска, убийство процессов PostgreSQL, остановку auth SQLite или стресс-нагрузку на production.** Для fault-injection использовать только отдельную disposable Compose-сеть, tmpfs размером 64-256 МиБ и два полностью тестовых аккаунта. Никаких команд `kill`, `truncate`, `rm` или SQL `DROP` в отношении production инстансов.

| Показатель | Предварительное событие |
|---|---|
| Свободно места | ниже 20% warning, ниже 10% critical сразу |

Снимать профиль реальной нагрузки в несколько этапов (2, 5, 10, 25 concurrent users) **только на выделенном стенде** с жёстким верхним лимитом и интервалами восстановления, если пройдены все младшие этапы; скрипт `api_load.py` пока задаёт максимум 16 рабочих потоков. Замерить CPU, RAM, disk IOPS/latency, PG active/waiting connections, WAL growth, pool saturation, очереди SMTP, p50/p95/p99 и throughput на каждой ступени. Настроить проверку удаления секретов из json/logs/alerts; отсутствие email и финансовых значений в агрегатах не означает отсутствия PII в сырых логах другого кода.

## RPO/RTO - цели и фактические значения

- **RPO целевой (для согласования): <=15 минут** для подтверждённых финансовых операций. В #79 полный backup по таймеру примерно раз в 6 часов: **этого недостаточно**, даже при успешном offsite. Нужна непрерывная доставка WAL/PITR либо явно согласованное ухудшение цели **до** публичного облака. Нельзя заявлять RPO 15 минут без замера последнего доступного consistent recovery point и тестового PITR.
- **RTO целевой (для согласования): <=60 минут** до работоспособного облачного API и авторизации с данными. Это порог, не измерение. Отдельно измерить восстановление PostgreSQL и SQLite, импорт GPG/ротацию ключей, включение сервиса, проверку сессий и возврат клиента из офлайна.
- Записывать monotonic start/end, UTC момент последней подтверждённой операции и recovery point, размеры и контрольные суммы **только синтетических** данных, вычисленный фактический RPO/RTO, точные SHA источника и PR, версии PostgreSQL и исполняемых инструментов. Без этих полей статус `NOT_VERIFIED`.
