# Financial Horizon #66 - PostgreSQL: эксплуатационный регламент

Статус: подготовленная инфраструктура, НЕ подтверждение production-развёртывания.
Контракт: docs/architecture/ADR-0065-cloud-finance-sync.md.
Auth SQLite и существующая IndexedDB не изменяются.

## Личный режим: без LUKS2 и отдельного сервера копий (решение владельца от 12.11.2026)

**Это действующий облегчённый контракт #66.** Разделы про LUKS2, SSH offsite, непрерывный WAL/PITR и RPO/RTO ниже относятся только к старому расширенному плану и **не являются условиями личного релиза**. Вместо них обязательно подтверждаем PostgreSQL, права, шифрованную копию и её фактическое восстановление. При потере VPS вместе с единственной локальной копией данные могут быть потеряны - риск принят владельцем.

Отдельный безопасный путь первой установки: `deploy/postgres/scripts/personal-bootstrap.sh`. Он не редактирует auth SQLite, другие БД, фронтенд, IndexedDB или OAuth. Функции финансового API по умолчанию выключены. Исходный `production-deploy.sh` остаётся строгим вариантом и **не используется для личного режима**.

В личном режиме дополнительно применяется `personal-loopback.override.yml`:
PostgreSQL доступна процессу FH-авторизации **только по адресу
`127.0.0.1:54329`**, с SCRAM и отдельной runtime-ролью. Публичный
PostgreSQL-порт не открывается. Строгий базовый Compose без опубликованных
портов не изменён.

На авторизованной VPS:

1. Подготовить свободный каталог `/srv/financial-horizon-finance/pgdata`, принадлежность PostgreSQL UID 999 и права 0700. Ничего не форматировать, не перезаписывать существующий DB volume. Допускается обычный диск VPS.
2. Сохранить **три разных** случайных пароля (минимум 32 байта) в `/etc/financial-horizon/finance/secrets/{admin_password,migrator_password,runtime_password}`, владелец UID 999, режим 0400; каталог root:root 0700. Значения не передавать в GitHub/CI/логи.
3. Подготовить `/etc/financial-horizon/finance/gnupg` (root:root 0700) с доступным локальным приватным GPG-ключом восстановления и `/var/backups/financial-horizon-finance` (root:root 0700). В root-only `/etc/financial-horizon/finance/backup.env` (0600) задать `FH_FINANCE_GPG_RECIPIENT` (40-символьный fingerprint), `FH_FINANCE_GPG_HOME` и `FH_FINANCE_BACKUP_DIR`. Приватный GPG-ключ на VPS является сознательным компромиссом простого режима; для защиты от потери VPS можно дополнительно хранить экспорт копии и ключа на доверенном устройстве.
4. В чистом checkout **последнего слитого main SHA с успешными точными CI** задать `FH_FINANCE_PERSONAL_MODE=YES`, `FH_FINANCE_DATA_DIR=/srv/financial-horizon-finance/pgdata`, `FH_FINANCE_APPROVED_SHA=<40-hex main SHA>`. Запустить от root `bash deploy/postgres/scripts/personal-bootstrap.sh`. Скрипт откажется стартовать при ошибке прав, доступного места, CI, секрета, ключа, сети Docker, миграций, RLS, шифрования или **реального изолированного restore**. При ошибке после запуска останавливает контейнер, не уничтожая данные.
5. Только после вывода `FINANCE_PERSONAL_BOOTSTRAP=PASS` создать root-only `/etc/financial-horizon/finance/start.env` (0600), содержащий указанные SHA, mode, data dir и `FH_FINANCE_CHECKOUT_DIR` с абсолютным путём checkout. Установить `fh-finance-personal.service`, `fh-finance-personal-backup.service` и `fh-finance-personal-backup.timer` из `deploy/postgres/systemd/` в `/etc/systemd/system/`, сделать `systemctl daemon-reload`, включить `fh-finance-personal.service` и таймер бэкапов. Старые strict units LUKS/offsite не включать.
6. Проверять ежедневно статус резервирования (`systemctl status fh-finance-personal-backup.service`) и наличие копий `*.pgdump.gpg`. При новом релизе нужна отдельная проверка миграций и восстановление **до** включения версии API. `personal-bootstrap.sh` сознательно блокирует попытку перезаписать уже существующий контейнер, это не скрипт обновления.

### Подключение финансового API после настоящего восстановления

После успешного запуска/restore на VPS существующий сервис
`fh-email-auth.service` должен использовать проверенную установленную версию
Python с `backend/requirements-finance.txt` и безопасно защищённые
переменные окружения (не в GitHub):

```text
FH_FINANCE_RUNTIME_MODE=personal
FH_FINANCE_V2_RUNTIME=on
FH_FINANCE_PROFILE_NAMESPACE=<один постоянный UUID, сохранять при backup/restore>
FH_FINANCE_DATABASE_URL=postgresql+psycopg://fh_finance_runtime:<URL-encoded password>@127.0.0.1:54329/fh_finance
```

`FH_FINANCE_PROFILE_NAMESPACE` создаётся **один раз** перед первым запуском и
не меняется при обновлениях: именно он связывает проверенного FH-пользователя
с постоянным финансовым профилем. Пароль берётся из отдельного runtime-secret
PostgreSQL; файл systemd-конфигурации должен быть закрыт от посторонних
пользователей. Не включать `FH_FINANCE_RUNTIME_MODE` и v2, пока не пройдены
реальные backup, isolated restore, проверка FH-сессии, Origin/IDOR и rollback.

По умолчанию обе опции `off`; приложение продолжает обслуживать существующий
email/OAuth и локальный PWA без финансового PostgreSQL. После включения
backend-оператор проверяет Caddy-маршруты `/api/finance/v1/*` и
`/api/finance/v2/*` к тому же авторизованному FH-сервису, без второго
публичного порта. Только после успешного smoke клиентский флаг
`<meta name="fh-finance-accounts" content="enabled">` разрешается доставить
проверенным релизом. Само слияние исходного кода флаги не переключает.

**Что ещё требуется для закрытия #66:** реальный авторизованный production-исполнитель, успешный запуск этой процедуры на VPS, новый зашифрованный архив, PASS изолированного восстановления, запись exact SHA/health и rollback. Зелёный CI и наличие скриптов не заменяют выполнение на VPS.

## Границы инфраструктуры

- PostgreSQL 17 с закреплённым digest официального образа; отдельный кластер,
  отдельный bind mount на **LUKS2-шифрованном устройстве**, приватная internal-сеть, без ports.
- Отсутствуют финансовый API, регистрация и публичная синхронизация.
- Роли fh_finance_migrator (DDL) и fh_finance_runtime (DML); runtime без
  SUPERUSER, BYPASSRLS, CREATEROLE, CREATEDB, DELETE, TRUNCATE и CREATE.
- Все 15 финансовых таблиц имеют ENABLE/FORCE RLS.
- Контекст principal через SET LOCAL после реальной проверки сессии в #67;
  RLS не заменяет API authorisation. Сырые SQL-запросы от клиента запрещены.
- Миграция Alembic и проверенные схемные SQL-файлы - единственный способ
  изменения структуры. Никакого SQLAlchemy create_all().
- Исходные auth SQLite, фронтенд и PWA остаются без изменений.

## Production preflight и запуск (только после gate)

1. Зафиксировать точный SHA, независимое ревью, PASS всех обязательных CI,
   RLS-интеграционные тесты, внешний backup и проверенный rollback.
2. Сверить CPU/RAM/диск и проверить отсутствие пересечений с другими Docker
   контейнерами, томами и сетями. Текущая VPS: Ubuntu 24.04.4 LTS,
   ориентировочно 4 GiB RAM и 13 GiB свободного места при первой проверке.
3. Создать /etc/financial-horizon/finance/secrets с правами 0700.
   Три разных файла admin_password, migrator_password, runtime_password
   с уникальными значениями не короче 32 символов. Для официального
   закреплённого PostgreSQL 17 UID пользователя postgres = 999 (проверить
   на образе до деплоя). Docker Compose file-backed secrets сохраняют
   права host-bind, поэтому файлы должны принадлежать UID 999, иметь
   права 0400, а каталог /etc/financial-horizon/finance/secrets
   принадлежать root и иметь права 0700. Иначе PostgreSQL инициализируется
   без финансовой БД. Мигратор запускается с тем же UID 999 и читает
   только отдельно подключённый миграционный secret. Не заменять это
   правами 0644/0444. Файлы и значения не передавать в git/issue/CI.
4. Подготовить отдельное зашифрованное LUKS2-устройство (или подтверждённый
   эквивалент), **не на диске другой БД**. Его ключ восстановления хранить
   только вне VPS, с отдельной проверенной копией. Не создавать LUKS
   автоматически из этого репозитория: опасность уничтожения существующего
   тома и компрометации ключа. На VPS монтировать разблокированный mapper
   строго в каталог финансовой БД, назначить UID/GID 999:999, права 0700.
   Проверить независимое offsite-хранилище резервных копий и возможность
   восстановления приватным ключом на доверенном устройстве.
5. Установить FH_FINANCE_DATA_DIR в точный абсолютный путь mountpoint,
   FH_FINANCE_MAPPER_NAME в имя выделенного LUKS2 mapper. Проверить:
   bash deploy/postgres/scripts/storage-preflight.sh
   Без подтверждения mountpoint, LUKS2 и имени отдельного устройства
   **стартовать DB запрещено**. Проверить Compose:
   docker compose -f deploy/postgres/compose.yml config --quiet
6. **Для первого production bootstrap используйте только**
   `deploy/postgres/scripts/production-deploy.sh` из чистого checkout
   слитого `main` с точным merge SHA и указанным reviewed PR HEAD.
   Задайте FH_FINANCE_APPROVED_SHA (merge commit) и
   FH_FINANCE_REVIEWED_HEAD_SHA (commit независимого APPROVED) через
   авторизованный операторский сеанс. Скрипт проверяет GitHub PR #79,
   независимый APPROVED на точном HEAD, 4/4 CI PASS для PR и main,
   фактический LUKS2, secrets и настройки offsite; без любого gate
   **отказывается запускаться**. После миграции проверяет RLS/порты
   и создаёт первую зашифрованную внешнюю резервную копию. Никакого
   автоматического включения финансового API/синхронизации нет.
   Прямая команда `docker compose up db` для производства запрещена.
7. Сверить finance.alembic_version = 0001_initial, pg_class с
   relrowsecurity=true/relforcerowsecurity=true для каждой финансовой
   таблицы, runtime-роли и GRANT, отсутствие published ports.
8. Проверить, что auth SQLite, страницы и текущие auth endpoints неизменны.

Запрещено: docker compose down -v, alembic stamp вместо upgrade,
применение reference SQL напрямую, изменение БД других сервисов.

## Защита, резервирование и восстановление

Публичный GPG-ключ получателя заранее импортируется на VPS в отдельный
закрытый keyring; приватный ключ хранится вне VPS на доверенном узле
восстановления. Файл backup.env задаёт FH_FINANCE_GPG_RECIPIENT и
FH_FINANCE_GPG_HOME; его права 0600. Backup dir
/var/backups/financial-horizon-finance имеет права 0700.

scripts/backup.sh потоково шифрует pg_dump -Fc открытым ключом без записи
открытого дампа на диск. Ошибки прекращают выполнение; файлы .partial
удаляются, завершённые копии хранятся 30 дней. Таймер systemd запускает
backup каждые шесть часов, но включать его можно только после ручного
успешного полного цикла backup/restore и настройки оповещений об ошибках.

scripts/restore-drill.sh принимает зашифрованный архив и восстанавливает его
в новый одноразовый PostgreSQL без сети/портов, затем проверяет количество
таблиц и pg_amcheck. Рекомендовано запускать его на независимом доверенном
узле, на котором хранится приватный GPG-ключ; не копировать этот ключ на
VPS ради удобства.

**Read-only WAL/PITR preflight (#66).** После отдельного разрешённого
развёртывания PostgreSQL можно выполнить от root
`deploy/postgres/scripts/pitr-preflight.sh` при настроенных
`FH_FINANCE_DATA_DIR=/srv/financial-horizon-finance/pgdata` и
`FH_FINANCE_MAPPER_NAME=fh-finance-pg`. Он проверяет состояние выделенного
LUKS2-тома, включённый `archive_mode`, безопасный `wal_level`,
настроенный архиватор, подтверждение успешного архивирования WAL за
последние 30 минут и отсутствие последнего неустранённого сбоя.
Скрипт ничего не записывает и не переключает WAL. Если хотя бы одна проверка
не выполнена, он сообщает `FINANCE_PITR_LOCAL_NO_GO` и заканчивается
ошибкой. Даже при успешной локальной проверке он явно выводит
`FINANCE_PITR_ENCRYPTED_OFFSITE=NOT_VERIFIED`,
`FINANCE_PITR_REAL_RESTORE=NOT_VERIFIED` и
`FINANCE_PITR_RPO_RTO=NOT_VERIFIED`.

Этот preflight не настраивает архивирование: в текущем Docker Compose
`archive_mode=on` и защищённое offsite WAL/PITR ещё не включены. Не
выдавать успешный `pg_dump` или синтетический CI за RPO 15 минут.
Для завершения #66 нужны отдельно настроенный реальный защищённый канал
WAL на независимый узел, проверка целостности, восстановление до точки
во времени и измеренный RPO/RTO на доверенной инфраструктуре.

**RPO/RTO пока не доказаны.** Цели ADR: RPO 15 минут и RTO 4 часа.
Без защищённого непрерывного WAL/PITR заявлять RPO 15 минут нельзя:
при расписании pg_dump каждые 6 часов RPO в лучшем случае до шести часов
плюс задержки/сбои. PITR и encrypted WAL здесь не настроены. Offsite-копии,
шифрование самого тома/диска и внешний мониторинг не подтверждены.
Локальный Docker volume с правами доступа не доказывает encryption-at-rest
и не защищает от потери VPS. RTO следует измерить отдельным restore drill.

## Независимый offsite и контроль отказов

По умолчанию штатный systemd unit запускает
`backup-and-offsite.sh`, который сначала создаёт локальную зашифрованную
копию, затем обязательно копирует **именно её** на отдельный узел
`offsite-upload.sh` по SSH с проверкой закреплённого ключа сервера
(`StrictHostKeyChecking=yes`) и контрольной суммы SHA-256 на удалённом
хосте. Если удалённый узел, конфигурация, ключ или проверка не работают,
service возвращает FAIL. Существующая локальная зашифрованная копия
при этом сохраняется, а не стирается.

Для этого **заранее**, вне git, требуются переменные в защищённом
`/etc/financial-horizon/finance/backup.env`:
`FH_FINANCE_OFFSITE_HOST`, `FH_FINANCE_OFFSITE_USER`,
`FH_FINANCE_OFFSITE_DIR`, `FH_FINANCE_OFFSITE_SSH_KEY`,
`FH_FINANCE_OFFSITE_KNOWN_HOSTS`, опционально
`FH_FINANCE_OFFSITE_PORT` (1-65535, по умолчанию 22), а также
существующие GPG-параметры. При нестандартном порте запись в
`known_hosts` должна закреплять `[hostname]:port`, проверять
отпечаток ключа назначения нужно через независимый доверенный канал.
Сервер назначения обязан быть отдельным отказным доменом и иметь
специального пользователя с минимальными правами, заранее созданный
каталог 0700, ограниченный SSH public-key доступ и проверенный host key.
Не допускается подменять удалённый узел локальным каталогом того же
диска или переиспользовать БД/секреты иных приложений. Хранилище
backup требуется проверять реальным restore drill и тестом отказа сети.

При отсутствии внешнего узла резервирование в production пока не
считается действующим. CI пока проверяет **отрицательный** сценарий
отсутствия offsite-конфигурации и локальный encrypted restore, но
не подтверждает реальную доставку удалённому узлу. Настройка внешнего
оповещения о неуспешном `fh-finance-backup.service` также обязательна
перед вводом в эксплуатацию.

## Rollback и безопасность обновлений

Проверить backup и restore ДО любых будущих структурных изменений.
Ревизия 0001_initial намеренно не позволяет разрушительный downgrade.
При ошибке до появления финансовых данных отключить/остановить только
новый финансовый сервис, сохранив том. После приёма пользовательских
записей только проверенный roll-forward или восстановление в новый
кластер с контролируемым переключением. Никогда не стирать аудит,
idempotency receipts и не выполнять DROP SCHEMA на production.

Не включать cloud до завершения #67-#70 и security #51.
CI backup/restore с синтетическими данными не заменяет фактический
production backup/restore. Без подтверждённого независимого review,
backup, инвентаризации шифрования и restore Issue #66 не закрывать.


## Обязательная защита физического хранения (новый блокер)

Compose не создаёт произвольный Docker volume и не подставляет незашифрованный
host-путь автоматически. Источник bind-mount берётся из обязательной переменной
FH_FINANCE_DATA_DIR, Docker create_host_path=false. Скрипт storage-preflight.sh
проверяет именно смонтированный каталог и сопоставляет его физический MAJ:MIN
с выделенным активным LUKS2 mapper. Имя задаётся FH_FINANCE_MAPPER_NAME.
Отсутствие разблокированного encrypted mount запрещает запуск. В CI негативный
тест подтверждает, что обычный временный каталог отвергается.

Это **защитный барьер перед развёртыванием**, а не выполненная настройка
шифрования на VPS: реальный контейнер на VPS и защищённое устройство ещё не
созданы, поскольку отдельно сохраняемый recovery key/провайдерская attestation
не предоставлены и нельзя генерировать ключ на незашифрованный корневой диск.



## Точный SHA и независимая приёмка (автоматизированный gate)

Скрипт production-deploy.sh требует отдельный GitHub `APPROVED` от пользователя,
не являющегося автором PR #79, на точном HEAD. Для продакшена нужен завершённый
GitHub merge commit именно этого PR, отдельно проверяются 4/4 PASS GitHub Actions
для reviewed HEAD и для main push merge SHA. Доступ к публичному GitHub API
идёт без токенов; сетевой сбой, пропущенный review или CI приводит к NO_GO.
В первый запуск запрещено переиспользовать существующий PostgreSQL-контейнер.
Скрипт не завершает эксплуатационную приёмку: после него требуется реальное
восстановление на доверенном независимом узле, измерение RPO/RTO, включение
проверенного резервного таймера и внешних уведомлений об ошибках.

## Согласование со счетами #33 (без перехода в облако)

Перед первой production-миграцией (текущая схема ещё не развёрнута)
в `finance.accounts` введено обязательное поле `kind`
(`bank`, `card`, `cash`, `savings`, `other`).
Начальный остаток `opening_minor` не имеет значения по умолчанию:
при добавлении счёта требуется явно передать целое число копеек,
включая `0`. Существующие IndexedDB и гостевые данные не
модифицируются, любое последующее облачное перенесение - только #69.

## Положительная проверка LUKS2 в CI

`ci-crypto-volume.sh` в изолированной GitHub Actions VM создаёт
одноразовый файловый образ, LUKS2 mapper и ext4, проверяет
`storage-preflight.sh` с отдельным разделом и затем размонтирует,
закрывает и удаляет только временный тестовый образ. CI-ключ
генерируется на runner, не попадает в артефакты, лог или production.
Негативная проверка обычного незашифрованного каталога сохранена.

Этот тест проверяет **код проверки шифрованного mountpoint**, а не
наличие защищённого production-тома и внешних ключей восстановления.
Не считать его фактической production encryption-at-rest.

## Восстановление RLS и GRANT

Архив сохраняет ACL (GRANT/REVOKE), но PostgreSQL cluster-level роли
не входят в `pg_dump`. На новом экземпляре PostgreSQL восстановление
выполняют **после безопасного создания отдельных ролей с новыми секретами**,
затем применяют зашифрованный архив с сохранением ACL и без смены владельца
на другого пользователя. Не использовать `pg_restore --no-acl`:
он удаляет привилегии runtime-ролей из восстановления. После восстановления
обязательно проверить 15 FORCE RLS, GRANT/REVOKE и отрицательные запросы под
`fh_finance_runtime`, а также реальную работоспособность финансового API
только после его реализации в #67. Изолированный скрипт `restore-drill.sh`
создаёт исключительно тестовую непривилегированную роль без пароля внутри
контейнера `--network none` и проверяет ACL и отсутствие контекста RLS.

## Disaster recovery - права владельца схемы

Зашифрованный custom-архив сохраняет не только GRANT/REVOKE, но и
`OWNER` финансовых объектов. При восстановлении в **новый изолированный
PostgreSQL кластер** сначала создаются новые непривилегированные роли
`fh_finance_migrator` и `fh_finance_runtime` с уникальными новыми
секретами вне Git. После этого архив применяется под ограниченным
восстановительным администратором с правом переназначить владельца.
Запрещено применять `pg_restore --no-owner` или `--no-acl`:
в противном случае будущие Alembic миграции или права runtime будут
сломаны при фактически успешном импорте таблиц.

`restore-drill.sh` создаёт в **одноразовом контейнере без сети**
тестовые роли без паролей, проверяет владельца `finance` и 15 таблиц,
RLS, ACL и `pg_amcheck`. В реальном восстановлении нужны новая
production-политика секретов и полноценный независимый тест под
авторизованной ролью после подключения #67.

## Безопасное создание миграционной и runtime-ролей

`init/10-roles.sh` читает только длину и отпечатки Docker secrets.
Пароли не передаются в `psql -v`, переменных окружения или аргументах
процесса. Текстовые секреты PostgreSQL считывает непосредственно из
`/run/secrets/*` через серверную функцию `pg_read_file` во время
первоначальной инициализации, а `format('%L')` безопасно экранирует
их при создании ролей. После завершения bootstrap PostgreSQL хранит
SCRAM-хэши в каталоге ролей. Параметры
`log_statement=none` и `log_min_duration_statement=-1` обязательны;
включать логирование SQL с параметрами паролей на этапе начальной
инициализации запрещено.


## P1: запрет незашифрованного повторного запуска PostgreSQL после reboot

**Безопасное поведение - STOP, а не plaintext fallback.** В Compose отключён
restart: unless-stopped; теперь restart: "no". Docker daemon НЕ должен
автоматически запускать PostgreSQL до разблокировки отдельного LUKS2-тома:
в противном случае существующий mountpoint на корневом диске позволил бы
создать второй незашифрованный кластер, минуя первоначальный preflight.

- Первый запуск только через production-deploy.sh с проверкой PR #79,
  независимого APPROVED, точного SHA, 4/4 CI, LUKS2, offsite и secrets.
  После Compose up проверяется фактическая Docker RestartPolicy.Name == no.
- Каждый последующий ручной запуск только через
  deploy/postgres/scripts/guarded-start.sh из чистого проверенного checkout.
  Требуется root, FH_FINANCE_APPROVED_SHA равный реальному HEAD и строгий
  LUKS2 storage-preflight до и после Compose up. При отсутствии тома FAIL.
- Для контролируемого запуска при boot есть отдельный, выключенный по
  умолчанию, deploy/postgres/systemd/fh-finance-postgres.service. Systemd
  unit зависит от отдельного mountpoint, вызывает лишь guarded-start.sh
  и при остановке не удаляет контейнер, базу, volume или журналы.
  Автоматически включать service до полноценной production-приёмки нельзя.

Только после настоящего production выпуска и настройки защищённого файла
/etc/financial-horizon/finance/start.env (root, 0600) с переменными:

- FH_FINANCE_CHECKOUT_DIR - абсолютный каталог чистого production checkout
  точного слитого SHA, не другого проекта;
- FH_FINANCE_APPROVED_SHA - проверенный 40-символьный release SHA;
- FH_FINANCE_DATA_DIR=/srv/financial-horizon-finance/pgdata;
- FH_FINANCE_MAPPER_NAME=fh-finance-pg;
- FH_FINANCE_SECRETS_DIR=/etc/financial-horizon/finance/secrets.

Оператор может установить unit в /etc/systemd/system/ и после
systemd-analyze verify выполнить systemctl daemon-reload и
systemctl enable --now fh-finance-postgres. Перед включением проверить
fstab/crypttab, отключённый том, последующее успешное монтирование,
отсутствие Docker auto-restart и готовность отката. Пароли/ключи LUKS2
никогда не записывать в unit/start.env или GitHub.

При недоступном LUKS2 PostgreSQL остаётся ОСТАНОВЛЕННОЙ. Команды
docker start fh-finance-postgres и docker compose up db в обход guard
на production запрещены. Проверять live reboot без отдельного разрешения
и независимых резервных копий недопустимо.

**Границы доказательств:** CI проверяет фактическую политику рестарта
одноразового контейнера, guarded-start и systemd mountpoint guard, но не
подтверждает поведение настоящего VPS после reboot, encryption-at-rest,
offsite восстановление или RTO. Эти проверки - обязательный gate #66/#70.

## P2: конкурентный settlement против смены направления обязательства

Старый guard_obligation_direction() запрещал последовательное изменение
направления после оплаты, однако FK KEY SHARE совместим с изменением
неключевого поля direction у обязательства. Новый BEFORE INSERT trigger
finance.lock_obligation_for_settlement() использует SELECT ... FOR UPDATE
строки обязательства, удерживая блокировку до COMMIT. Создание оплаты и
изменение направления теперь сериализованы в обоих порядках; проверка
знака проводки остаётся отложенной до COMMIT.

Новые интеграционные тесты на настоящей PostgreSQL с двумя соединениями
и ограниченным lock_timeout проверяют обе последовательности: ни смена
до оплаты, ни оплата до смены не допускают расхождения направления и
подписанной исторической проводки.
